# v2 late64 candidate (validation and four-pass confirmation passed; combo pending)

This isolated variant keeps FP32 exceptional-value checks eager and moves FP64 component/per-accumulation non-finite checks to a final block scan. Its patch, source/build hashes, CSVs, per-phase comparison, and gate result are archived in the adjacent metadata/comparison JSON and `v2_late64_gate_summary.json`.

Root reports that the frozen-v1 gate passed 100 cases and 2,322,780 C slots bitwise with zero mismatches, CTest passed, and four overflow/cancellation probes passed. The recorded 5-repetition CSV shows N=8192 FP64 p21 wall median 649.6 ms against 744.3 ms averaged from the eager before/after medians; N=4096 p21 is 76.5 ms against 99.6 ms. N=8192 p6 is only about 3.7% faster against those controls, and root reports p6 gains are not stable. These results justify the queued alternating p6/p21 confirmation, not an adoption claim.

The four-pass alternating confirmation is complete: N=8192 p21 medians were 681/654 ms in the two late64 passes versus 754/763 ms in the eager passes; N=4096 p21 was 89.3/89.8 ms versus 96.2/93.9 ms. N=1024 was mixed because its first eager pass was slower while the second was close to late64. Pooled phase/wall/fault values and source CSV hashes are in [the confirmation comparison](../v2_late64_confirm/comparison.json). Root proposes using late64 for FP64 K≥4096 and retaining eager checks below that range. The bounded-commit + late64 combination is still being compared and must pass before the production version is frozen. No production file was modified in this archive task.
