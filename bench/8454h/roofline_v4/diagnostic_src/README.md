# Roofline V4 diagnostic source preparation

This is an isolated preparation tree copied selectively from the immutable V3 release archive. It contains the production core/header, V3 oneMKL and optimization benchmark drivers, representative validation sources, a separate copy of the existing binary gate, and an untouched frozen V3 core/driver for bracketing. No vendor tree, old search history, campaign result, or frozen archive was copied here. Nothing in the active root implementation or immutable archives was edited.

The four `OZV4_MODE` values compile-time select these paths:

| Mode | Build tag | Meaning |
|---:|:---|:---|
| 0 | `mode0_control` | V3 behavior in the isolated mode-capable source. The bracket baseline links the immutable V3 release archive library directly. The mode build must pass the binary comparison gate before its performance run. |
| 1 | `mode1_diagnostic_plain_nf` | FP32 reconstruction remains in the original arithmetic order, while the eager FP32 non-finite check on each accumulated `block + micro` result is omitted. The current V3 FP32 accumulator only checks that reconstructed sum; it has no separate product-vector scan. Treat this as a finite-input diagnostic and do not read its measured error metrics as an accuracy pass. FP64 retains its V3 component-product and accumulated-result checks. |
| 2 | `mode2_diagnostic_no_reconstruction` | FP32 and FP64 still generate the same AMX component products, in the same order, with the same FP64 batch scratch/load/store path, preparation, private zeroed output blocks, and private-result copy. Product accumulation is omitted, so output is expected to be zero. This is a timing-only, non-numeric diagnostic: CSV profile rate, speedup, and error fields are `NA`, with `accuracy_scope` and `status` both set to `diagnostic_no_reconstruction_non_numeric`. The memory barriers keep the private block observable to the compiler so its scan/copy work cannot collapse around the expected zero. |
| 3 | `mode3_candidate_late32_unvalidated` | FP32 uses the existing eager path when K<4096. At K>=4096 it performs the unchanged microproduct and BK256 additions without a per-micro non-finite test, then scans the completed private cache block once with 16-float AVX-512 loads. Pure IEEE addition cannot recover a finite value from an Inf/NaN prefix. The private result is committed only after the scan. FP64 follows its existing V3 eager/Late64 selection. This is a candidate only; correctness and transactional guarantees still require the dedicated numeric gate. |

Dispatch chooses the mode template at the API entry or the K>=4096 boundary, not inside the microtile accumulation loop. All mode builds use the fixed Sapphire Rapids target, `-ffp-contract=off`, `-fno-fast-math`, and the V3 tuning defaults. Distinct mode source IDs and tags prevent checkpoint reuse between builds.

## Sequence after the paper-campaign freeze

`run_sequence_after_freeze.sh` refuses to start until a freeze marker exists and the immutable V3 archive library has SHA-256 `73f0764610072b05a3e50afb8ce312fe6b717c361efef7b94e52f20bde63b42c`. The default marker path is `bench/8454h/v3_paper_alignment/FROZEN_COMPLETE`; set `OZV4_FREEZE_MARKER` to the signed completion marker when the 66-configuration V3 paper supplement has been completed and frozen. The runner holds `/tmp/ozamx-perf.lock` across the bracket sequence and uses that exact V3 archive for the initial and final controls. Before mode 0 or mode 3 performance output, its isolated build must pass all three CTests and `tools/run_binary_gate_v4.py` must pass full-buffer byte comparison and transaction/exception semantics against the archive. Mode 1 and mode 2 remain diagnostic-only and are never labeled accuracy-validated. The binary gate includes the existing large FP32/FP64 output cases plus FP32 K=4096 overflow, cancellation, NaN/Inf transaction, and A=C/B=C alias cases; its JSON preserves each side's full-output SHA-256, exception kind/message, and unchanged-C result. Default workload is N=1024/4096/8192, 64 CPUs, five timed calls, one warmup, 2 GiB workspace cache, uniform data, and the same V3 driver arguments. `OZV4_SIZES` can add a selected size such as 16384 if the host's available memory supports the three dense matrices. Each output, checkpoint family, executable/library hash, and source/freeze hash gets its own path under `results/`.

This source-preparation session has not configured CMake, compiled code, executed tests, run a benchmark or binary gate, or touched the live performance lock. The isolated `tools/roofline_binary_gate_v4.cpp` and `tools/run_binary_gate_v4.py` implement the V3 full-output comparison and FP32 K=4096 exception/transaction/alias cases; these gates remain unexecuted until the paper-campaign freeze. The existing archived gate and its historical results stay untouched.
