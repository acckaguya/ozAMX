# ozAMX 项目总结：论文复现、平台优化与现阶段结论

本文整理截至 **2026 年 10 月 14 日** 的项目状态，把论文方法、机器特点、代码演进、性能测试、精度问题和实验记录放在一起说明。详细报告和原始数据仍保留在各自目录；这里侧重解释它们之间的关系，让不了解前面工作的人也能读懂项目为什么这样实现、哪些结论已有证据、哪些问题仍未解决。

当前工作树版本为 **0.4.0**。V3 的论文对齐补测已经完成并冻结，随后的一轮 roofline 搜索也已收齐。现行代码采用了范围有限的 FP32 分块优化：最终同批对照中，4096 阶和 8192 阶方阵的完整 API 平均耗时分别减少约 **4.1% 和 7.6%**。FP64 的论文精度差距仍然存在，完整 GEMM 也还没有接近热寄存器微基准显示的算力水平。

## 1. 这个项目要解决什么问题

项目复现的是论文《BF16 Component-Product Emulation of FP32 and FP64 GEMM on Intel AMX》，本地论文位于 [third_party/papers/2609.04663v1.pdf](../third_party/papers/2609.04663v1.pdf)。这是独立实现，围绕论文描述重新组织了分片、打包、AMX 计算、结果累加和验证流程。

GEMM 是通用矩阵乘法。项目的核心任务可以写成 `C = A × B`，其中 A 的形状为 M×K，B 为 K×N，结果 C 为 M×N。论文的实验主要使用实数方阵；本项目接口还覆盖矩形、带行间距的矩阵，以及部分输入与输出共用内存的情况。

FP32 是通常说的单精度浮点数，FP64 是双精度。BF16 是一种 16 位浮点格式，指数范围接近 FP32，但小数精度少得多，所以需要多个分量一起表示较精细的输入。tile 可以理解成 AMX 寄存器保存的一小片二维矩阵；SIMD 则是一条指令同时处理多个普通向量元素。

论文的思路是利用 AMX 的 BF16 矩阵点积能力：先把精度较高的输入拆成几个 BF16 分量，用多个 BF16 矩阵积近似原来的矩阵积，再按指定顺序恢复 FP32 或 FP64 结果。这个办法把一次高精度计算变成了多次低精度计算，因此性能取决于两件事：AMX 做这些小精度乘法能有多快，以及分解、搬运、求和等额外工作要花多少时间。

项目因此一直同时追踪两条线。数值线上，要确认实现是否遵循论文的公式、舍入和产品集合，并解释误差差异。性能线上，要把 CPU 的向量和矩阵单元用起来，减少标量处理、无效内存访问和重复分配。只完成其中一条，都不足以称为成功复现。

论文阅读、公式及图表核对的详细过程见 [PAPER_STUDY.md](PAPER_STUDY.md)，当前数值契约见 [REPRODUCTION_SPEC.md](REPRODUCTION_SPEC.md)。

## 2. 论文方法怎样落到计算流程里

### FP32：三片输入，六项乘积

每个 FP32 输入被依次拆成三个 BF16 分量。可以把它理解为：第一片保留主要部分，后面的片继续表示前一步没能表示的余量。A 和 B 都有三片；展开相乘共有九种组合，算法保留其中六种较重要的组合。

当前实现保持论文式子所要求的物理累加顺序：`11、10、20、00、01、02`。例如 `10` 表示 A 的第 1 片与 B 的第 0 片相乘。浮点加法会发生舍入，同一组数按不同顺序相加，结果可能不同，因此这个顺序属于算法的一部分。

FP32 路径的汇编内核会复用已经加载的分量。例如同一个 A 分量可以连续与多个 B 分量计算，减少重复 tile 加载。每个 K32 步进执行 24 条点积指令和 14 次输入 tile 加载；这是当前内核的实际工作安排，而非六次普通 GEMM 简单串联。

### FP64：六轮投影，按预算保留部分乘积

FP64 的分解使用论文给出的全局余量尺度和 `rho=45`。rho控制投影网格的尺度；当前实现固定为45。每一轮先观察当前余量的最大绝对值，确定投影尺度，再通过指定的 double 舍入和 BF16 舍入得到一个分量，随后更新余量。公式中的舍入位置必须保留，不能为了向量化随意重结合加减法。

计算提供四档产品预算：

| 名称 | 实际保留的输入分片数 d | 计算的分量矩阵积数量 | 含义 |
|---|---:|---:|---|
| p6 | 3 | 6 | 成本较低，省略的尾项较多 |
| p10 | 4 | 10 | 增加一层分量组合 |
| p15 | 5 | 15 | 进一步保留较小分量的贡献 |
| p21 | 6 | 21 | 当前论文方法中最高的产品预算 |

这些名称表示矩阵积数量，不表示保留多少十进制有效数字。各档使用 `i+j<d` 的产品集合。实现会保存对应的 d 片，但仍保留六轮投影及必要检查；“只存三片”和“只执行三轮分解”不能混为一谈。

AMX 把每个分量积累加成 FP32 临时结果。FP64 路径在指定 BK 边界把这个结果存出，独立拓宽成 double，再按规定顺序累加到 FP64 结果。先把多个产品合并在 FP32 里，再统一转成 double，会改变数值过程，不能直接当作等价优化。

### 为什么输入 double 不代表结果就是完整 double GEMM

结果误差还来自输入分片的尾部余量、未计算的产品、AMX 内部的 FP32 累加，以及最后的浮点求和。p21 虽然使用最多的分量积，也不能据此保证对所有输入都得到正确舍入的 double 结果。论文给出了经验实验，本项目也需要通过具体指标和输入范围说明精度。

当前支持域还有限制。FP64 有限非零输入的绝对值需处于 BF16规格化数（normal）的范围，即约 `2^-126` 到 `(2−2^-7)×2^127`，零允许。NaN、Inf、域外值、非零BF16非规格化数（subnormal）分片及影响结果的 AMX 中间溢出或下溢不属于已支持情形。代码没有通用缩放或自动高精度回退。硬件内部将极小数直接清零（FTZ）造成的静默下溢也不能仅靠 `isfinite` 检查全部发现。具体边界以 [REPRODUCTION_SPEC.md](REPRODUCTION_SPEC.md) 为准。

## 3. 当前 CPU 有什么能力，哪些能力被用到了

原代码来自 Xeon Gold 6430 环境，当前机器是双路 **Xeon Platinum 8454H**。这两个型号都属于 Sapphire Rapids；更换型号不等于跨越了一个指令集代际。频率、缓存、内存和整机配置会影响表现，代码仍需要适应具体的数据和工作集。

当前测量快照记录的主要条件如下：

| 项目 | 当前记录 |
|---|---|
| CPU | 2 路 8454H，每路 32 个物理核、每核 2 个逻辑线程 |
| 总计 | 64 个物理核、128 个逻辑 CPU，2 个 NUMA 节点 |
| 常用测试绑定 | CPU 0–63，使用每个物理核的一个线程，横跨两个 socket |
| 缓存 | 每核 2 MiB L2，整机两路合计约 165 MiB L3 |
| 系统及编译器 | Ubuntu 22.04.5、Linux 5.15.0-161、GCC 11.4、GNU OpenMP |
| oneMKL | 当前对照使用 2026.1、GNU 线程层 |
| 频率条件 | powersave，频率未固定 |
| 测量限制 | 共享主机；`perf_event_paranoid=4`，未取得 PMU 计数器 |

AMX 和 SIMD 在这里承担不同任务。**AMX** 负责 BF16 分量矩阵积；**AVX-512** 负责分片中的整数舍入、余量更新、重排、格式打包、FP32 到 FP64 的转换、结果累加、尾部处理和非有限检查。AVX/AVX2 的资料和实例也已收集，但现行主路径主要围绕这台机器的 AMX 与 AVX-512 能力实现。

NUMA 表示不同 socket 附近有各自的内存访问区域，跨 socket 访问会增加通信成本。测试输入由调用线程生成，打包工作区由线程团队分工写入；复用缓冲区也可能沿用此前的页面放置，并不等于每次重新分配、按当前线程布局首次写入。操作系统还可能迁移页面，实际放置和迁移没有得到连续验证。因此只绑定 64 个核，并不能说明数据一定均匀地分布在两路内存中。PMU 是硬件性能计数器，可帮助观察缓存失效和其他硬件事件；当前没有取得这些计数，所以后面的瓶颈讨论需要保留这一边界。

AMX 有 8 个 tile 寄存器，一个 tile 最多 16 行、每行 64 字节。本项目用两个 A tile、两个 B tile 和四个 C tile 组成 32×32 输出微块，正好占满这八个寄存器。因此增加预加载或同时保留更多产品，往往需要重新安排寄存器，而不是多加几个临时量就能实现。

本机可用 AMX-TILE、AMX-BF16、AMX-INT8，以及相关 AVX-512 扩展。AVX-512 FP16 和 AMX FP16 是独立能力，不能看到前者就推断后者。AMX 还需要操作系统的扩展状态支持和进程许可；运行时会检查 CPUID/XSTATE 并申请许可，各工作线程配置和释放自己的tile状态。

官方资料、白皮书和代码参考位于 [third_party/intel/README.md](../third_party/intel/README.md)。资料库包括 Intel SDM、优化参考手册、Intrinsics Guide、SKU 页面、AMX/BF16/SIMD 示例、oneDNN 相关实现及 Linux XSTATE 说明。来源、版本、获取日期和哈希都有记录；研读笔记围绕与项目有关的章节展开。Linux 大页和 oneMKL dispatch/verbose 文档另保存在 `third_party/manuals/`。

## 4. 一次矩阵乘法实际要做哪些工作

代码的主要流程是：检查尺寸与输入，拆出 BF16 分量，打包成 AMX 方便读取的格式，分块执行点积，把临时结果累加还原，最后提交给 caller 的 C。

“打包”是把原来按普通行列保存的数据，改排成 tile 可直接读取的面板。尤其 B 的 BF16 相邻 K 元素需要配对组织。当前完整 tile 的行 stride 为 64 字节，SIMD 重排生成对应格式；不足一个向量或 tile 的尾部使用 mask，padding 明确置零。

几个尺寸概念需要分开理解。32×32 是 AMX 组合后的输出微块，K32 是一次内部点积推进的深度，BK=256 是一次 FP32 部分和存出与还原的边界，而 128×256、128×512 或 256×256 是外层组织工作和缓存复用的宏块。改变外层宏块可以保持每个输出的求和次序；改变 BK 则可能改变 FP32 部分和的舍入，所以不能把它们视为同一类调参。

结果先写入私有缓冲区。计算成功后才提交到 caller C；若检测到不支持的值或中间溢出，就抛出错误，并保持 caller C 原有内容。这也使输入和输出部分共用内存的情况可以正确处理，但需要额外工作区和最后提交成本。

工作区池属于调用线程，按精确大小复用缓冲区。每个池有 64 个槽位，当前默认最多保留 **2 GiB**，可通过 `OZAMX_WORKSPACE_CACHE_BYTES` 调整，设为 0 可关闭保留。这个数字是每个池保留的逻辑字节上限，不是进程 RSS 上限，更不包括用户的 A/B/C、正在使用的缓冲区、线程栈和内存分配器自身开销。具体定义见 [`preprocess.hpp`](../src/preprocess.hpp)。

预处理和结果处理已经大量 SIMD 化。软件实现的 BF16 RNE 舍入用于保持原有位模式和支持域检查，避免硬件转换的 FTZ 行为悄悄改变数值定义。大矩阵还采用分片与打包融合，减少中间数组和额外遍历；因此某些 profile 中单独的 pack 时间接近零，是这项工作被并入了 split 阶段，并非打包不再有成本。

## 5. 原实现为什么会与论文表现相差很大

前期结果给出了可定位的实现成本：串行分片、标量打包和还原、面板布局不适合 tile、每次调用的大量分配与初始化，以及输出工作集安排不合理。它们会让 AMX 频繁等待，或让加速后的乘法在完整调用中只占很小一部分。

早期同机对照中，4096 阶 FP32 的 split 均值曾从约 111.95 ms 降到 2.47 ms，compute/reconstruct 从约 83.26 ms 降到 20.29 ms；FP64 p6 的 split 从约 280.45 ms 降到 11.76 ms。这些历史数据说明，初始差距有明显的软件实现因素，并不能仅用 CPU 型号差异解释。

同时，本机与论文平台不相同。论文使用双路 8462Y+、Rocky Linux 9.3、Intel 编译器/OpenMP；这里使用 8454H、Ubuntu、GCC/GNU OpenMP，频率未固定，主机也不独占。论文没有披露完整的随机数生成器与 seed。我们已经尽量对齐尺寸、输入分布、线程数、重复次数和指标，仍不能把它们视为同一平台的直接性能复测。

剩余差距也有算法成本。FP32 要计算六项产品，FP64 最高要计算二十一项；分解、打包、还原和事务性提交都算在 API 内。单个 BF16 kernel 的峰值不会自动转化成一次完整 FP64 GEMM 的速度。最新测试表明，即使内核正确、AMX 可用，完整程序仍有很大的供数和组织成本待解释。

历史实现与同机优化证据见 [8454H_PERFORMANCE_BASELINE.md](8454H_PERFORMANCE_BASELINE.md)。该文件中的“当前版本”等措辞属于当时记录，今天的状态以本总结和 [8454H_CURRENT_BASELINE.md](8454H_CURRENT_BASELINE.md) 为准。

## 6. 版本怎样逐步演进

项目的性能记录不是一条可以首尾相接的加速曲线。不同阶段换过源码、缓冲区上限、采样次数和测量协议，所以每一组数字只回答它自己那次对照的问题。

| 阶段 | 主要变化 | 已保存的主要证据 |
|---|---|---|
| V1 | 手写 AMX 内核，SIMD 分片/打包/还原，tile 面板和工作区复用 | 与旧实现在同一8454H上的匹配对照及逐位审计 |
| V2 | 融合分片与打包，收敛预处理粒度和加载提示，采用 late64 检查及2 GiB缓存 | 50个搜索任务、2292个计时重复、独立保留样本测试、oneMKL对照 |
| V3 | 按大矩阵形状与精度调整宏块及重建批次 | 正式oneMKL矩阵、V2/V3匹配复核、66项论文对齐补测 |
| 当前0.4.0 | 在规定范围内为FP32选择256×256宏块 | 23项完整门、OpenMP/无OpenMP检查、实际主代码逐次交替对照 |

V1同机匹配旧实现时，N=256/1024/4096观察到的速度约为旧版的2.85–12.03倍；8192扩展约为2.90–3.82倍。这些是早期旧实现到V1的结果，不表示对oneMKL有同样优势，也不能与后续版本的比例连乘。

V2阶段需要区分两份记录：早期隔离候选使用1 GiB工作区缓存，冻结生产构建使用2 GiB。它们不能合并成一个“V2速度”。这一阶段的参数搜索完成50个任务和2292个计时重复，还保留了512/2048阶的独立验证样本；具体设置与身份见 [V2冻结说明](../bench/8454h/versions/v2_release/README.md) 和 [参数搜索结果](8454H_SEARCH_RESULTS.md)。

V3的补充匹配重测使用V2/V3/V2/V3/V2五进程序列。每配置每进程计时七次，先求进程内中位数，再比较三个V2进程和两个V3进程的中位数汇总。N=8192的结果如下，单位毫秒；它们属于这个历史批次，不能与今天的主代码均值表混用。

| 模式 | V2 API中位数 | V3 API中位数 | V3耗时减少 |
|---|---:|---:|---:|
| FP32 p6 | 186.705 | 149.744 | 19.8% |
| FP64 p6 | 282.815 | 216.841 | 23.3% |

这个结果说明V3在该轮大矩阵对照中有收益，但小矩阵和不同预算的变化并不一致。当前0.4.0的范围、均值结果和采用理由单独放在第11节。

## 7. 论文对齐补测与精度现状

V3冻结库完成了一组与论文 Table 4、Figure 8 和 Figure 6 对应的本机补测：40个精度/尺寸配置、18个FP32线程扩展配置、8个原始BF16 oneMKL吞吐配置，共66项。主表覆盖方阵阶数256至32768，FP32六积和FP64四档预算；每项先预热一次，再计时十次。这里的随机输入由本机固定seed生成，论文没有给随机数生成器或seed，因此这是协议对齐的重复实验，不是对论文相同矩阵的逐项重算。完整范围和记录见 [V3论文对齐报告](8454H_V3_PAPER_ALIGNMENT.md)。

精度比较使用两项指标。相对Frobenius误差为 `eF = ||Chat−Cref||F / ||Cref||F`；scaled最大误差为 `e_scaled = max_ij (|Chat−Cref|ij / (|A||B|)ij)`，其中 `Cref` 是oneMKL SGEMM或DGEMM结果。前者概括整个输出的相对误差，后者关注单个元素相对于该位置绝对乘积和的最大偏差。分母为零的特殊情况需要单独说明，不能照常相除。论文数值和缩放因子的逐尺寸表在 [复现规范](REPRODUCTION_SPEC.md)。

本机FP32 p6的误差量级与论文接近，FP64则明显偏高。八个阶数上，实测误差与论文误差之比的中位数如下：

| 模式 | eF实测/论文 | e_scaled实测/论文 |
|---|---:|---:|
| FP32 p6 | 1.004 | 1.003 |
| FP64 p6 | 5.701 | 5.563 |
| FP64 p10 | 11.146 | 10.835 |
| FP64 p15 | 21.916 | 21.856 |
| FP64 p21 | 8.207 | 4.404 |

这些是八个阶数的实测值与论文表值之比，不是误差阈值，也不表示每个尺寸恰好相差同样倍数。论文Table 4的比较细节和范围见 [V3论文对齐报告](8454H_V3_PAPER_ALIGNMENT.md)。日志中的运行成功状态，也不表示精度已经匹配论文。

精度证据有不同覆盖范围，不能相互替代。主表中的oneMKL `eF` 和 `e_scaled` 都遍历完整N×N输出；独立binary128直接乘法诊断只对N≤256计算全矩阵，高阶只随机抽取512个输出位置，所以高阶样本不能当作完整Frobenius误差。本机的 `long double` 使用x87扩展精度，虽然占16字节，也不是binary128；真正的四倍精度诊断使用 `__float128` 和quadmath。

N=256的独立诊断中，字面rho=45的FP64-p21 `eF` 约为6.4076×10^-15，而论文表值为5.71×10^-16。该单点诊断将误差追到终端余量与省略产品：两部分相对Frobenius量约为4.032×10^-15、5.002×10^-15，但这不是任意输入的误差界。另试过带符号尺度的rho=44投影变体，单点误差可以接近论文量级；它同时改变了分解定义，不能证明论文使用了这个变体，也没有作为生产替代方案。详细证据见 [FP64诊断](FP64_DIAGNOSTIC.md)、[带符号尺度诊断](SIGNED_SHIFT_DIAGNOSTIC.md) 和 [原生内核审计](NATIVE_KERNEL_AUDIT.md)。

原生审计还逐项检查了147,456个分量/BK边界的FP32 AMX存出结果，以及730个FP64重建审计输出；被审计的乘积计算、打包和输出顺序均通过相应逐位检查。这里的730个输出是诊断所覆盖的测试点，不是所有公开FP64接口输入的覆盖数量。这说明已审计的底层计算没有显示出足以解释FP64差距的偏差，但不能证明论文算法的截断误差来源，也不能覆盖任意输入和全部支持域。差距仍未解释；未知的论文seed、平台差别或成功运行状态，都不足以单独解释它。

## 8. 性能结果应该怎样读

一次完整API调用和其中某个阶段是不同的计时对象。API墙钟包括分片、打包、计算与重建、调度以及相关分配/释放；阶段profile只回答时间落在哪一部分。oneMKL对照记录的是SGEMM/DGEMM那次GEMM调用本身，并不包含ozAMX的分片与打包。AMX热寄存器校准则把输入tile预先放在寄存器中，反复运行点积，省掉矩阵遍历、打包和完整结果恢复。四者可以用来定位成本，却不是彼此可直接相除的同口径完整产品。

常见的 `2N³ / API时间` 是按一次普通目标精度GEMM的数学工作量计算的“有效吞吐”。它方便和普通GEMM的工作量放在一起看，但没有把ozAMX实际执行的多个分量积数进去。若按产品数 `p` 计算 `2N³p / 时间`，得到的是产品操作数等效吞吐：FP32 p6的 `p=6`，FP64则按p6/p10/p15/p21取对应产品数。这个数仍含该计时阶段里的其他成本，不能称为AMX真实发射速率。比如N=8192当前FP32 API的普通有效吞吐约4.354 TFLOP/s；其计算/重建阶段按六积折算约28.080 TOP/s。前者和后者回答的问题不同，不能把约26.126或28.080 TOP/s写成普通单次FP32 GEMM吞吐。热寄存器约161 TFLOP/s又是独立微基准的局部参考，不是完整API可达到的已证上限。

比较两个实现时也要读清统计量。算术均值会受到少数长样本影响；中位数描述排序后居中的样本；“均值之比”是两边均值相除；“配对比值的中位数”则先逐次相除，再取中位数，它们通常不同。当前0.4.0与冻结V3的核心结果采用持续运行的两个子进程逐次交替调用，固定输入并核对完整输入哈希和C输出哈希；两边均报告64个工作线程绑定在CPU 0–63。复核使用GNU OpenMP默认等待设置，每次API调用后在计时外停20 ms。报告保留所有样本，因此离群长调用会影响均值；如N=16384样本数少且波动大，均值可能显得很好看，但中位数和逐次结果不支持强速度结论。这个结果更适合说“本批次观察到”，而不是据单个均值推断普遍性能。

项目的性能锁只保证本项目自己的重型测量任务不同时运行，并不独占整台服务器。其他负载仍可能竞争核心、带宽和频率；频率策略也没有固定。因此跨报告、跨时间段的读数只能在协议匹配且原始记录支持时作有限比较。尤其不能把早期V1加速、V2/V3的中位数改善、0.4.0的配对均值和另一时段oneMKL参考连续相乘成一个总加速倍数。原始样本与批次边界分别保存在 [历史匹配基线](8454H_PERFORMANCE_BASELINE.md)、[V3 roofline结果](8454H_ROOFLINE_RESULTS.md)、[当前机器基线](8454H_CURRENT_BASELINE.md) 和 [0.4主线验证](8454H_V4_CURRENT_MAIN_VALIDATION.md)。

## 9. 如何读 roofline：机器潜力不等于整机 GEMM 速度

Roofline把吞吐限制画成两条线：算力上限，以及数据供给造成的上限。简化公式是 `吞吐 ≤ min(计算上限, 运算强度×带宽)`；运算强度就是每搬运一个字节能完成多少运算。矩阵块复用更多，运算强度通常会上升；可复用空间不足、数据反复读取时，供给成本就会变大。不过公式里的工作量、字节数和带宽必须采用同一口径、同一存储层级。AMX指令读取的逻辑载荷不能直接当作DRAM实测流量。

仓库后来建立了分层 roofline 和一组核级校准，目的是把“硬件能做多快”“数据按某种布局供给时能做多快”和“完整 API 实际花多久”拆开，用来提出下一轮可验证的优化假说。三类数不能互换：AMX 寄存器微基准把输入 tile 预先放入 tile 寄存器，测点积单元的热上限；带实际 tile load、SIMD 转换和 FP64 重建的小工作集混合内核多了一部分供数与累加成本，但仍是小工作集；完整 API 还包含分片、打包、分派、线程/tile 状态、输出提交和释放。尤其 FP64 p21 的“去重建”诊断没有返回正确 GEMM 结果，只能当作局部供数参考，不能称为算法加速。

2026-10-14 的同机校准测得以下64线程读数，均按分量积的运算数量计数：

| 校准对象 | 观测吞吐，TFLOP/s | 该读数涵盖什么 |
|---|---:|---|
| AMX寄存器驻留点积 | 161.018 | 热tile反复点积，基本不含矩阵搬运 |
| FP32六积，仅产品 | 155.550 | 小工作集供数与产品计算 |
| FP32六积混合核 | 151.738 | 小工作集产品及结果恢复 |
| FP64 p6混合核 | 84.423 | 小工作集产品、转换及重建 |
| FP64 p21混合核 | 86.306 | 小工作集产品、转换及重建 |
| FP64 p21去重建诊断 | 123.239 | 不返回正确FP64 GEMM结果的局部测量 |

这些是各自计数口径下的观测，不是Intel承诺的峰值，也不证明当前完整计算路径能达到它们。该轮有57项校准配置，每项预热一次、计时三次，保存了171个计时样本。此前另一个批次的AVX-512寄存器FMA校准，64线程FP32约9.9678 TFLOP/s、FP64约5.0778 TFLOP/s；它们提供向量单元的局部参照，不能与本轮AMX样本组成严格配对。更多方法、重复性和数据见 [V4校准报告](8454H_V4_ROOFLINE_CALIBRATION.md)、[本轮结果](8454H_V4_ROUND_RESULTS.md) 和 [历史机器基线](8454H_PERFORMANCE_BASELINE.md)。

完整矩阵的吞吐也有两种分子。按用户请求的一次 GEMM 有效工作量 `2N³` 计，8192 阶 FP32 当前 API 是 **4.354 TFLOP/s**；若把算法实际执行的六个 BF16分量矩阵积 也计入，则同一 API 时间对应的分量积操作数等效吞吐是 **26.126 TOP/s**。只看 compute/reconstruct 阶段则为 **28.080 TOP/s**。三者分别回答“用户做完一次 GEMM 多快”“按分量积计数后完成了多少工作”“仅计算重建阶段吞吐多大”；它们不是同一个标准。28.080 与热混合核 151.738 的比值约 18.5%，只能说明这两项不同工作集、地址跨度、阶段边界和测时窗口之间有距离，不能称作 AMX 利用率、瓶颈占比或“还剩 5.4 倍可提速”。

还需避免把不同测量范围的带宽拼成一条带宽上限线。同台8454H的早期独立内存基线报告的 64 线程 copy/triad 逻辑流量约 **188.54/190.88 GB/s**，属于历史独立数组流式测试；它的读写字节按程序逻辑访问计数，write-allocate 等实际流量可能不同。它不是物理 DRAM 峰值，也不是当前 GEMM打包面板的有效带宽。新triad与tile-load测试的工作集规模、输入首次触页和 NUMA 摆放都不同，不能把旧 triad 数字直接配给当前 tile-load 逻辑字节。当前性能记录里没有 PMU cache miss 或 DRAM 流量计数，故不能据 roofline 图断言具体落在 L1、L2、LLC 或内存上。相关边界见 [分层模型](8454H_ROOFLINE_MODEL.md)、[流量说明](8454H_ROOFLINE_TRAFFIC.md) 和 [历史校准](8454H_ROOFLINE_CALIBRATION.md)。

AMX 与 AVX-512 的独立峰值也不能直接相加。一个 GEMM 阶段里，AMX tile 计算、AVX-512 分片/转换/重建、缓存供数及共享端口会竞争或相互制约；是否重叠取决于真实依赖和调度。模型应按阶段列 `t ≥ max(W/P, Q/B)`，其中计算能力 `P` 和带宽 `B` 必须与该阶段、同一数据边界匹配；串行 split、pack、compute、commit 时间可以相加，但同一 compute 阶段各自独立的 AMX与SIMD算力上限 不能简单相加成一个生产上限。Tile load 记出的 TB/s 是指令逻辑载荷速率，不能被重命名为“DRAM 带宽”。

## 10. 最近一轮 65 组搜索学到了什么

V3 冻结后进行的 V4 roofline 搜索共有 **65 组计时参数配置**，这个数字是实验配置的累计数，不是 65 种互不相同的算法。组成是 29 组宏块/重建 batch、16 组打包间隔/分量轮转、8 组 AVX-512 重建开关、6 组 padding/加载提示、4 组页面对齐/大页提示、2 组 AMX 加载分组，其中包括控制和重复配置。一个默认 OpenMP 栈下崩溃的候选不算有效计时配置；INT8 原型虽做了精度验证，但没有进入性能矩阵。完整过程和逐轮链接见 [V4搜索日志](8454H_V4_SEARCH_LOG.md) 与 [V4本轮结果](8454H_V4_ROUND_RESULTS.md)。

首先测试了“把更多 K 累加留在整数里，最后再还原”这条 INT8 路线。原型把八个有符号 radix-128 数位组合成 36个分量积，以 8 个整数对角线累加，并在结尾用 INT128 舍入到 double。它在 16个精度测试 中有 3 个没有通过预设精度要求：K=1、小量稀疏乘积，以及 A/B 指数互相抵消的动态范围输入；最后一类 `e_scaled` 约 0.291。没有因为失败而放宽门槛，也没有跑性能矩阵。即使先只数点积指令，INT8 K 深度 64 带来的理想指令数也只是 V3 p21 的 6/7，理想纯计算比约 7/6（1.167 倍）；它有 36 个积而非 21 个，量化、打包和最终重建也要计入。1.167只是纯点积指令的理想比值；整体收益还取决于分片、打包和还原，不能把它当作完整API的速度上限，也不能据此声称INT8一定快两倍。详见 [INT8实验](8454H_V4_INT8_EXPERIMENT.md) 和 [成本模型](8454H_V4_COST_MODEL.md)。

保持现有浮点数值契约的尝试也没有自动转化为稳定收益。调整宏块与 FP64重建批次能找到局部可行区域，但小尺寸任务数减少会带来退化，N=16384 的候选平均耗时收益在保留慢样本后反转；打包间隔、A/B slab 轮转、AVX-512 八链重建、padding、TILELOAD/TILELOADT1、不同 AMX 加载分组均有工作负载间取舍，或被共享主机时序漂移淹没，未形成足够稳定的默认胜者。扩大的输出块还曾在默认栈配置下崩溃，扩大栈后的结果只作为诊断，未算质量通过。THP 提示确实获得了大页映射，但交替复测均值、中位数及调用位置效应不一致；没有 TLB miss 计数，不能断言 TLB 是瓶颈，也没有因此改变 内存分配器默认值。失败、慢样本和不采用结论都留在相应日志里。

若干结果说明了阶段成本的重要性，但不是可以发布的数值实现：去掉 p21 重建后，某个 8192 诊断 compute 阶段约缩短 19%，却不产生有效的 FP64 数值结果。局部“去重建”点因此不能转述成完整 API 提速。packed 数据的实际几何也经复核：FP64 一个 slab 是 **16 KiB**，八个 slab 的面板是 **128 KiB**；先前把产品数当成存储片数的容量估算不成立。p6/p10/p15/p21 的存储深度分别是 3/4/5/6 片，产品数则是 6/10/15/21，容量模型应使用深度 `d`，不能拿产品数 `p` 代入。

对N=8192，FP64输入A+B的BF16分片逻辑体量按d=3/4/5/6约为 **0.75/1.0/1.25/1.5 GiB**。此外，一份完整私有FP64结果矩阵是 **512 MiB**，一份double余量数组也是 **512 MiB**；用户的double A/B/C合计还需约1.5 GiB。这些是按数组形状估算的逻辑载荷，不是同时存活对象的精确峰值，也不是进程RSS测量。默认2 GiB工作区池只限制可复用缓存的保留量，不能据此推出进程只用2 GiB，或把上述数字简单相加就认定峰值。工作区复用能避免部分反复分配，但也会使页面放置更依赖此前调用，需要按具体形状和内存预算评估。搜索日志与成本说明见 [搜索日志](8454H_V4_SEARCH_LOG.md)、[成本模型](8454H_V4_COST_MODEL.md) 与 [打包布局结果](8454H_V4_PACKED_LAYOUT_RESULTS.md)。

## 11. 当前 0.4.0 实际采用了什么，观测到什么结果

当前 0.4.0 只采用了一项有严格输入范围的 FP32 宏块选择：当使用默认 `CACHE_BLOCK=128`、FP32 的 `min(M,N)≥4096`、`max(M,N)≤8192` 且 `4096≤K≤8192` 时，输出宏块从原来的 128 几何改用 **256×256**。其余形状继续走既有路径；显式设置非默认 cache block 时也不强行启用这条分支。FP64 的各档产品预算没有采用本轮的几何改变。

这项局部改变保留了原算法的数值检查和执行顺序：BK 仍为 256，K32 内累加方式及 FP32 六项产品的顺序不变，64 字节行 padding、非有限检查、私有C成功后再提交的事务语义、工作区缓存行为也保留。采用理由是 N=4096 和 8192 的 FP32 收益经匹配对照复现，而扩大到 N=16384 时收益因慢样本反转；独立 N=4096 的 FP64 p6 也未复现此前候选收益。所以这个启用条件来自实测边界，不是“越大越快”的推断。完整参数、约 1228 KiB 到 1044 KiB 的逻辑工作集估计（不等于缓存流量）和取舍见 [V4本轮结果](8454H_V4_ROUND_RESULTS.md)。

实际主代码通过 OpenMP 和无 OpenMP 各 3 项 CTest；完整对照验证 **23/23** 通过，覆盖原 20 项、4097×4099×4096 的 padding 和完整输出、优化范围内 A=C 别名，以及溢出拒绝时 caller C 保持不变。无 OpenMP 的 4096³ 完整结果也与冻结 V3 逐字节一致。这些验证说明所测路径保持既定输出与错误事务行为，不代表支持范围以外的矩阵或所有浮点输入均已证明正确。主代码身份、完整验证记录 和逐调用数据在 [当前主线验证](8454H_V4_CURRENT_MAIN_VALIDATION.md) 中。

性能复核让冻结V3与当前主代码各自静态链接到独立常驻进程中，按调用逐次交替；64个物理核、输入、线程绑定和2 GiB缓存配置匹配，每次调用之后的20 ms等待不计入API时间。每次均核对完整输入与C输出哈希、64个工作线程的CPU放置，样本全部保留：

| FP64 p21 | 8192 | 1019.4521 | 295.3353 | 0.290 |

该批次4096阶FP32的ozAMX均值较低，其他项目均高于对应oneMKL调用。FP64产品预算上升时，需要做更多分量积和重建，完整成本也随之上升。ozAMX与DGEMM的精度定义并不相同，速度表需要结合第7节的误差现状阅读。

这组测试使用被动OpenMP等待及零自旋设置，是单独的三次样本批次，不能与上面的默认等待、V3匹配交替数据拼接计算新的加速比。原文件仅保留MKL三次均值，缺少逐次时间，也不能补造每次配对数据。ozAMX计的是完整API，SGEMM/DGEMM计时是GEMM本身，比较时需要交代这一边界。

独立的oneMKL verbose诊断确认了运行库宣称的版本、GNU线程层、线程数和可用指令集，但“支持AVX-512/AMX”不等于证明每次调用确实发出了某条特定指令。安静计时批次没有完整记录ISA限制环境变量，后来诊断中的环境不能倒推为该批次原值。详见 [当前主线验证报告](8454H_V4_CURRENT_MAIN_VALIDATION.md) 的补测说明。

例如，在这台机器的项目根目录可以用以下命令新建一个临时Release构建并运行基础CTest。三步共用一把性能锁，失败时停止后续步骤；它不会重跑论文66项补测或23项完整门，也不会覆盖冻结包：

```sh
flock /tmp/ozamx-perf.lock bash -c '
  set -e
  cmake -S . -B /tmp/ozamx-review-build \
    -DCMAKE_BUILD_TYPE=Release -DOZAMX_ENABLE_OPENMP=ON
  cmake --build /tmp/ozamx-review-build -j8
  OMP_NUM_THREADS=64 OMP_PLACES=cores OMP_PROC_BIND=close \
    taskset -c 0-63 ctest --test-dir /tmp/ozamx-review-build --output-on-failure
'
```

记录中的错误也要保留上下文：早期FMA微基准曾因相同初值的累加链被编译器合并，导致工作量计数过高，后续已改用独立链并核对反汇编；旧读数不作为有效基线。搜索图表也修正过GFLOP/s到TFLOP/s的换算，原错误图保留在失败目录并标记无效。V4的候选图表示实验候选，不能直接当作0.4.0有限启用范围的全尺寸曲线。最终判断应回到源码身份、实际计时和报告口径。

下一步的精度问题应先分清输入数学、分片与截断定义、参考库求和差异和AMX指令语义，再决定是否提出独立算法变体。任何改变rho、分片公式、产品集合、FP32求和树、FP64拓宽与相加顺序或终端余量处理的方案，都应单独通过精度验证并保留失败数据。

性能问题则应先补齐与实际工作集、NUMA首次触页、缓存层级相匹配的证据。目前没有PMU物理流量数据，仅凭逻辑字节或热寄存器比值无法确定瓶颈。若改变完整流程的结构，要同时报告完整API、各阶段耗时、精度验证、错误时输出保护和适用范围，并与冻结V3在相同调用范围下复测。现有搜索没有穷尽全部几何、线程和系统状态，当前版本是已验证的局部选择，尚不能称为全局最优。
