## 最需要独立验证的闭环

原有 `2N³/秒` 算式重算正确，不足以独立证明“本次输入的完整 GEMM 已执行”。最重要的闭环是：确实要求完整 M×N×K；计时包住同步返回的完整例程；每次新输入对应的完整输出经过与 MKL 无关的校验。三者成立后，再从 raw seconds 重算单位与统计。

1. **工作量和输出新鲜性。** 检查 N/ld、RowMajor/NoTrans、alpha=1/beta=0、完整 A/B/C 长度，输入变化/poison 在计时外且输出全矩阵都被使用。不能只读一个 checksum 或投影一个角落。raw BF16 的 oracle 必须使用实际 BF16 解码值；若用原 FP32 A/B，必须先证明它们逐项 BF16 精确可表示。
2. **计时完整与同步。** 两个独立 wall clock 均以秒保存；routine 返回即完成输出，不把 CPU time 当 wall time。数据生成、oracle、投影、poison、输出 CSV 不应混入 timer。多个 clock/API 的读取本身会产生固定开销，尤其小 N；保留两墙钟边界差异而不是无说明地选择更快一个。
3. **精确数值模型。** 对 dyadic 输入，明确整数单位和输出分母。证明每个乘积、partial sum、N128 oracle、B×r、A×(B×r mod p)、C×r 所用整数类型均不溢出。不能先把 C 浮点数截断/四舍五入成整数，再把非整数错误掩盖掉；必须先验证 C 有限且落在期望精确格点。
4. **随机投影的范围。** 最初的八个 ±1 向量方案已被主代理替换：实际源码使用素数 `p=2147483647` 上三个完整随机向量，并在每次输出产生后重新从 getrandom 取样。这不是逐元素精确证书，应给出精确域概率界和适用条件，不能把 sample/概率检查写成全输出逐项 oracle。
5. **防消除。** 外部 GEMM 结果需进入实际可观察的全输出验证；不以声明 volatile 代替输出消费。查看循环参数和输出检查可证明工作未被 benchmark 自己省略；对于未知库内部的特化，不能仅凭计数公式声称指令数。
6. **统计。** 一次预热、十次 timed，保留全部原始 wall/CPU、顺序、seed、校验结果；用 `2N³/mean(wall)` 作主吞吐，均值/中位数/mean(1/time) 分别标清。单进程各 routine 随机交替有助于状态匹配，但若某库保留 spinning worker，它仍可影响下一例程，不能称独占机器。

## 受控 dyadic 输入的解释限制

若所有 A/B 都是小整数乘 2 的整数次幂、且 BF16 精确可表示，原有 FP32 split 的低两片通常为零。这个设计很适合排除“旧输出/少算完整矩阵/错误计时单位”，也允许精确整数 oracle；但它不能单独担保所有一般 FP32 三片均非零输入的精度或性能。应明确这是受控输入下的计时与完整性证据，不能把三个有限域投影称为完整逐元素 oracle，也不能用这样的输入证明 FP64 的论文 Table 4 误差已经解决。

## 实际源码：形状、执行和计时

`main:194` 将 N 限制在 128、1024、4096；caller A/B/C 都分配 N²。三个例程均传完整 `(N,N,N)`、leading dimension N、RowMajor/NoTrans、alpha=1/beta=0（`207-209`）。ozAMX 调用公开非 profiled API，故内部 dispatch、split/pack、compute、提交/清理都包含于 routine 的同步返回。外部例程的结果 C 后续经过全数组 hash、finite 检查及数学验证，benchmark 没有无消费的死结果；没有以旧 benchmark 算出的 checksum 当 truth。

两个墙钟的嵌套边界为 `cpu0 → raw0 → steady0 → GEMM → steady1 → raw1 → cpu1`（`206-211`）。`CLOCK_MONOTONIC_RAW` 由秒和纳秒构造 double 秒，steady 使用 `duration<double>`，单位正确。RAW 包含额外 steady-clock 读取开销；CPU 还包含墙钟读取开销。CPU 是进程所有线程 user+system 的总时间，可高于 wall，不能拿来作吞吐分母。两个 API 读取路径可以交叉检查边界和单位，但在 Linux 上不等于两个独立物理时钟源。

`mutate:89-102`、全 C NaN poison（`205`）、调用前/后输入 hash、oracle、getrandom、挑战文件写入和 CSV 输出都在计时之外。每个 N/family 的 round=-1 是每 routine 一次预热；round=0…9 是十次计时（默认 reps10）。每 round 三个 routine 的输入相同，顺序以独立 splitmix 状态洗牌（`198-200`）。uniform 的 raw BF16 使用其真实 ah/bh 解码值作 oracle（`158-159`），没有拿未量化 FP32 数组当其 truth。

默认计划共 `2 family × 3 N × 11 round × 3 routine = 198` 次例程调用，其中 18 次预热、180 次正式计时。另有两次故意破坏 C 的验证器调用，不包含新的 GEMM 例程、不进入计时行。

源文件本身不计算 TFLOPS；应从 `warmup=0` 的原始记录以 `2*N³/mean(raw_wall_s)/1e12` 重算，并同时给 steady 口径检查。数据生成和验证会显著触碰内存并改变后续 cache/等待状态；这仍是受控 harness 条件，不应宣称等同旧 campaign 或独占主机。

## 完整 dyadic 校验的数学核查

输入为 `A=Ai/16`、`B=Bi/16`，Ai/Bi 在整数 [-8,8]（`77-81`），变更后仍在范围内。因此真实输出 `Cinteger=256*C=Ai*Bi`，每项绝对值至多 `64N`。乘积及任一合法 partial sum 的整数单位界远低于 2²⁴，所以在这个受控输入上，三个例程应得到精确可表示的 FP32 输出，不需要浮点误差容差。

代码先全矩阵 finite 检查（`109-110`），再对每项 `256*C` 检查 `trunc(x)==x`、`abs(x)<=64N`，最后才转 int32（`112-118`）。这不会通过整数转换掩盖非格点的小错误。N128 另有全部 16384 个输出的逐项 int64 dot oracle（`120-126`）。

三个 Freivalds 挑战在输出及 hash 完成后抽取（`128-147`）。采样接受 uint32 的 `[0,2p-1]`，拒绝最顶端两个值，再 `%p`，所以每个域元素恰有两个原像；不是不均匀的直接 uint32 模 p。检查的是 `Cinteger*r == Ai*(Bi*r mod p) mod p`，行列索引一致，mod 对负数归一到 `[0,p)`。

独立整数上界重算（均使用最坏绝对和，未依赖取消）：

| N | `max abs(Cinteger)` | `sum abs(Cinteger*r)` 上界 | `sum abs(Ai*(Bi*r mod p))` 上界 |
|---:|---:|---:|---:|
| 128 | 8192 | 2251799811588096 | 2199023253504 |
| 1024 | 65536 | 144115187941638144 | 17592186028032 |
| 4096 | 262144 | 2305843007066210304 | 70368744112128 |

最大的左侧界严格小于 2⁶¹，右侧也远小于 int64 上限；Bi*r 的单独累加同样受 `8N(p−1)` 约束。当前维度范围内没有这里的 signed overflow。若未来扩到更大 N，必须重新证明上界，不能无审查删掉范围限制。

若某错误输出通过格点/幅度检查，错误矩阵每项绝对值至多 `128N<=524288<p`。所以任何非零整数错误矩阵在 Fp 中也非零，不会因恰好是 p 倍数而完全消失。对输出完成后抽取的独立均匀向量，单挑战漏检概率至多 1/p；三个至多 `p^-3≈1.0097419601e-28`。默认 exact family 的 3 尺寸×11 次（含 warmup）×3 routine 共 99 个输出，保守 union bound 至多约 `9.9964454e-27`。这是在 getrandom 随机性、独立挑战与整数模型成立条件下的理论界，**不是已经运行通过的声明**。

## 一般 FP32 输入的独立点积诊断

uniform 生成式 `83-84` 把有符号整数除以 2²³，变更 ±0.25 也保留同一格点。N128 检查全部输出，大 N 固定选择 512 个索引（允许重复），各自用独立 long double 的 K 项 dot 和绝对乘积和作误差参照（`150-166`），阈值 `max(error/(abs(A)abs(B)))<=5e-6`。它不是论文 Table 4 全矩阵 eF/e_scaled。

还有一项可用的精确性证明：输入是分母 2²³、绝对值不超过 1 的数；每个乘积可写成分母 2⁴⁶ 的整数，N4096 的全部绝对整数和至多 2⁵⁸。若 `numeric_limits<long double>::digits>=64`，这些点积乘法/加法本身可以精确表示。raw BF16 量化只会把这组输入的格点变粗，仍适用上述上界。本机是否满足以 stdout 的 `long_double_digits` 为准；若迁移到 long double=double 的平台，不能沿用这份精确性证明。

**采样新鲜性缺口已补：** 首版每轮 uniform 只改一个 A 元素，固定 512 样本不保证覆盖受影响行。最终 `mutate:93-100` 改为在每个输出行改变一项 A，并同步更新 ah；每个被抽样行都因本轮输入变化而被重新考验。这增强了识别旧输出的能力，但采样和误差阈值仍不能证明完整一般 FP32 矩阵逐项正确。完整 NaN poison 可识别没有写回的 C 槽位；完整 hash 仅记录结果身份，不替代数学 oracle。

**输入不变性缺口已补：** 最终 `203-204` 在每 routine 前 hash 实际输入（ozAMX/SGEMM 为 float A/B，raw BF16 为 ah/bh）；`214-216` 在两个 wall 和 CPU 区间结束后、oracle 之前重新 hash。`inputs_unchanged` 进入 all_ok（`218`）、CSV（`219`）和错误日志（`221`）。若输入被误写，即使 uniform oracle 随着数据变化，整个实验仍会失败。这是 64-bit FNV 完整遍历的不变性 gate，不是抗恶意哈希碰撞的密码学证书；当前目标是发现实现错误。

## 记录完整性修订与独立负控

**写盘缺口已补：** 最终 `178-183` 检查三个输出文件打开成功，并对 CSV、挑战二进制、negative-control JSONL 全部启用 failbit/badbit exceptions；`246` 在发布最终 pass 之前 flush 三个 stream。tellp/write/flush 失败会触发异常并返回 2，而非静默丢掉挑战/CSV 后仍报告成功。`entropy:62-64` 也已补 EINTR 重试。

最终 `225-240` 在 N1024 dyadic 的 ozAMX 预热校验之后加入两种故意错误：单元素加 1/256，以及整个 C 清零。它们复用相同验证器、独立抽取新挑战，要求 mismatches>0；N1024 不走小矩阵逐项 oracle，所以该负控检验的是有限域/格点 gate，且全部位于例程计时之外。原 C 随后恢复。负控日志包含 mismatch、实际挑战数、oracle_entries、challenge_offset。最终实测时应确认两个负控确实失败、challenges=3、oracle_entries=0，不能只确认正常路径输出 pass。

挑战二进制用本机 uint32 序，重放时还需记录 endianness、N、round、routine、offset、三个向量共 `12N` 字节及对应输入生成规则；负控也消耗挑战文件空间，不能只按正常 CSV 行顺序推算 offset。程序没有自行记录完整编译、库、环境、affinity 身份，需由主代理外层运行证据补全。

## 审查结论范围

最终源码未发现核心完整调用、墙钟单位、dyadic 格点转换、有限域乘法索引或 int64 溢出的确定错误；首轮提出的三项证据缺口已经修订并复核。可以据此进入主代理安排的正式 198-call 实验；这是对受限 harness 设计和最终源码的确认，**不是对尚未运行结果的预先认证**。

剩余限制必须伴随结果保留：dyadic 低片为零；uniform 大 N 仅 512 点、可重复且阈值为 5e-6；两个墙钟非独立物理源；CPU 时间不能作 wall 吞吐分母；输入 hash 不抵抗恶意碰撞；验证、hash 与写盘会改变下一调用的缓存/调度状态；配置64不等于每个内部阶段实际64；共享主机非独占；FP64 论文精度不在此附件范围。原始计时、正常/负控校验、挑战字节数及运行身份仍须在实验完成后独立分析。
