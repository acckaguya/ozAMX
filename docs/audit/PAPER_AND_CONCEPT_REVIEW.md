审查日期：2026-10-15。范围：本地 `third_party/papers/2609.04663v1.pdf`，然后对照 `docs/PAPER_STUDY.md`、`docs/REPRODUCTION_SPEC.md`、`docs/8454H_V3_PAPER_ALIGNMENT.md`、`docs/PROJECT_SUMMARY.md` 及相关数值诊断报告。本次未修改实现、未重跑性能实验，也未把既有报告中的实验当作本次重新验证的实验。以下明确区分原文事实、数学推导、仓库记录和待确认事项。

## 1. 结论与证据边界

论文提出的确实是两个不同的数值过程：FP32 三片六积共用 FP32 tile 累加；FP64 六片、6/10/15/21 项，每个组件积的 FP32 结果分别存出、拓宽并加入 FP64 输出。它不是通用 FP64 GEMM 的等精度替代，Table 4 是特定均匀随机输入的经验结果，不是误差上界（§4–5，pp.8–12；§8.2，pp.20–21）。

目前复现的关键差距应拆成两个独立问题。FP64 精度首先涉及分片投影和截断误差，不能优先归咎于 CPU 型号或 MKL 速度；性能首先涉及端到端执行路径、预处理、线程运行时和数据流，不能用热寄存器峰值直接解释。现有 V3 报告显示 FP32 精度接近论文，但 FP64 各预算误差系统性偏大，同时多数大尺寸端到端加速未出现。这支持“协议覆盖完成，数值及性能结果未完全复现”的表述，不能支持“论文已完全复现”。

需要特别避免一个错误诊断：**FP32 组件积不必然留下 1e-7 误差地板。** 公共 shift 产生的格点与 BK=256 可以使单个组件 partial dot 精确，见第4节。反过来，这种精确性也不能消除六片终端残差和被截断的产品，不能单凭它保证 Table 4。

此 PDF 没有给出作者实现仓库链接；这只说明该文档不能提供作者实现的直接核对入口，不能推断作者代码不存在。本文没有借用非官方外部材料；原文定位均指本地 PDF。

## 3. 数学集合、物理顺序与未确定的循环层级

FP32 的 Eq.(10) 在p.8按00,01,10,02,11,20展示产品，Algorithm 1在p.9的双循环产生00,01,02,10,11,20；Eq.(19)在p.15明确改为11,10,20,00,01,02。三者保留的集合相同，浮点过程不同。论文已明确以物理复用顺序执行，故不能用Algorithm 1表面循环次序替代式(19)。

单个AMX输入tile只容纳K32，BK为256（§6.1，p.13）。因而实际执行还有八个K32步。实现选择“K32外、六项链内”可以在一个K32步中实现14次tile load；若“产品外、完整BK内”，不能直接通过相邻产品共享当前寄存器恢复同样的整体复用。论文 §6.2 的面板措辞将BK与tile序列压缩叙述，未给完整循环代码。必须把具体嵌套写为复现选择，并核查实际load/store数，而不是只抄14这个数。

FP64 Algorithm 2（p.11）规定对角线层级递增，线内写“for all”而未指定i递增；现有文档采用i递增是合理且可重现的约定，不是作者明确给出的唯一顺序。Eq.(16)写full-K组件积的数学抽象；§6.3则给出了分块执行与逐组件微核重建。**每BK partial widen/add与full-K后一次widen/add可能不同**，尤其当FP32归约不能证明精确时。现有 `REPRODUCTION_SPEC.md` 对此保留“不宣称作者唯一调度”的注释是正确做法。

FP64共用FP32累加器跨多个不同(i,j)产品，会丢掉它们之间不同尺度的低位，违反p.11及p.16描述。将同一产品的连续K32累加到BK结束则是另一件事，不应误判为跨产品累加。

## 4. FP64 shift的真实语义与条件性精确点积

### 4.1 原文公式

对当前残差R（§4.3，p.10，Eq.(13)–(14)）：

```text
v = ceil(log2(max(abs(R))))
sigma = 2^(v+45)
Z = fl64(fl64(R + sigma) - sigma)
Xr = round_BF16(Z)
Rnext = fl64(R - Xr)
```

整块残差为零时后续置零。sigma是正的、在作用域内共享的幂次，并非 `copysign(sigma,R)`。R+sigma必须真的舍入到FP64，不能由编译器重结合成R。式子给出矩阵max，但周围也称vector/panel；§6并行分块不充分说明作者到底对全矩阵、面板、行/列计算max。当前全局max策略应明确是对公式矩阵写法的落实；要确认作者实际作用域需作者伪码或切片样例。

### 4.2 正负侧不对称：这是改变误差谱的实质条件

以下为本审查从公式推导，不是论文已有定理。设正常范围、round-to-nearest、无下溢，|Rij|≤2^v。sigma是2的整数次幂。对正R，R+sigma在sigma上方，FP64网格步长为 `2^(v−7)`；对负R，结果在sigma下方，步长为 `2^(v−8)`。因此字面正shift给正负残差不同的投影分辨率。它不能泛化成“每个值统一保留8个有效位”，也不能等同普通BF16 RN逐元素分解。

`rho=44`、对每元素使用带符号shift、以及直接BF16 residual rounding，分别改动不同条件。即使某个变体更贴近Table4，也只能成为独立算法假设，不能静默替换字面rho45实现。

### 4.3 BK=256为何可能使FP32组件partial精确

令每片公共网格 `qA=2^(vA−8)`、`qB=2^(vB−8)`。上述投影产生的chunk可写为 `a=l*qA`、`b=m*qB`，其中整数满足 `|l|,|m|≤256`。正侧只占其中偶数格点；负侧可占相邻格点。这些chunk在受支持正常范围内可存为BF16，符合论文所述Z=stored slice（p.10）。

一个长度≤256的组件dot，其每个部分和都是 `qA*qB` 的整数倍；其绝对值以该单位计不超过 `256*256*256=2^24`。FP32可以精确表示绝对值≤2^24的整数。因此，**若参与该归约的A片/B片各共享上述尺度，乘积及中间和没有指数范围损失，则该组件BK partial的乘积及累加可以精确表示为FP32**。这也解释为什么BK边界可能是数值条件，而不只是缓存参数。

该充分条件不自动覆盖：每个K元素有不同投影尺度的拼接；延长BK；普通逐元素BF16舍入；超范围或subnormal乘积；把多个不同尺度的组件积混合到同一FP32累加器。论文§5.2在p.12只给定性误差讨论，未把这个条件作为完整定理说明。应验证实际分片格点和归约边界，而不能仅套一般BF16点积最坏误差界。

### 4.4 零片与支持域文字存在需要澄清的边界

p.5、p.10说低残差片变成subnormal或zero不受支持；但p.10同时明确整残差为零则余下片全部置零，而且公共网格必然使某些小但非零残差投影为零，随后仍可保留残差在后层提取。最合理的工程解释是：精确零和投影量化零允许，因BF16指数下溢导致信息丢失的非零片不支持。**这属于消解文字歧义的解释，不能把它写成论文逐字明确允许所有投影零。** 现有 `PAPER_STUDY.md` 的“只有非零subnormal超域”表述宜标注这一解释边界。

## 5. Table 4能否由公开方法保证

不能保证。作者明确将其定位为[-1,1]均匀随机输入的经验测量（§8.2，pp.20–21），没有给seed/RNG、完整求和树或可推出每个表值的误差定理。

Table4的eF数量级分别为：FP32约3.02e-7至4.58e-7；FP64-p6约1.49e-8；p10约3.25e-11；p15约6.96e-14；p21约5.71e-16至1.46e-15（p.21）。最后一档接近DGEMM差异量级，并不等于正确舍入或相对精确AB的同样误差。

应建立如下误差分解（本审查分析框架）：

```text
原始实数AB
  → stored slices的完整36项实数和       [分解终端残差/残差更新影响]
  → 选中6/10/15/21项实数和             [产品截断]
  → 每BK组件的实际FP32结果             [组件归约及指数边界]
  → 既定顺序的FP64重建                 [重建舍入]
  → 与oneMKL DGEMM比较                 [参考自身误差及相减]
```

这些误差可能抵消，不能把各阶段误差范数当可直接相加的精确等式；需要同一输入上的矩阵差或高精度残差。

现有仓库证据指向分解/截断优先：`REPRODUCTION_RESULTS.md`记录literal p21与高精度AB约6.36e-15，且组件store已做独立比较；V3对齐报告记录p6/p10/p15的eF倍率分别约5.70/11.15/21.92，跨尺寸相当稳定。上述是既有实验记录，不是本子审查重复计算。主审本轮另已重跑独立分解，证据在 `docs/audit/evidence/literal_fp64_recomputed.json`：selected21约6.407642639e-15、terminal约4.032335e-15、omitted约5.001517e-15、selected21FP32delta为0；主审亦报告新N256 p21对MKL约6.3872768e-15，以及147456个component store零不匹配。这些由协作主审提供的当前证据加强了数学分解/截断优先的判断，本文没有将其冒充自身重新执行的结果。稳定并随预算变化的倍率，比“不同CPU”或“不同随机seed”更像分片误差谱存在系统性差异，但尚不足以判定作者实现。

`SIGNED_SHIFT_DIAGNOSTIC.md`记录一个非作者、单输入、N=256替代公式：带符号rho44投影。其p6/p10/p15误差接近论文的1.49e-8/3.26e-11/6.95e-14，p21对MKL约5.48e-16。它是高价值解释线索：统一更细格距可能改变截断尾部而匹配论文谱。它仍不能证明作者实际用了该公式，更不能把一个样本称为论文重现成功。特别要保留该诊断oneMKL2026.0与V3 2026.1的区别。

## 6. TFLOPS、有效工作量和raw headroom

原文§7.4（p.19）规定有效吞吐为 `2N^3/T`，因为目标问题是一次C=AB。对应单位转换必须写清：

```text
有效GFLOP/s = 2N^3 / (T_seconds * 1e9)
有效TFLOP/s = 2N^3 / (T_seconds * 1e12)
有效TFLOP/s = 有效GFLOP/s / 1000
逻辑组件乘加工作量约 = Np * 2N^3
```

最后一项是组件工作，不含split/pack/store/convert等开销；它不是目标GEMM的有效吞吐。不能把21项内核的组件TFLOPS与DGEMM的有效TFLOPS放在同一列解释成应用加速。

图6（p.20）的轴和caption确实标GFLOPS，最大柱值38.08；图7–9也标GFLOPS。现有本机raw BF16记录约38.8 TFLOP/s，这使“原图误写单位”成为合理怀疑，但不是已证事实。必须同时保留原印刷值与本地明确定义单位，不能自行把图6改成38.08 TFLOP/s并宣称已对齐。以N=16384为例，2N³约8.796e12；若38.08 GFLOP/s则约231秒，若38.08 TFLOP/s则约0.231秒，相差1000倍。没有作者原始时间或勘误，不能解决此歧义。

单位疑点不影响图内同单位时间比，但影响跨平台绝对值比较。FP32六产品在raw BF16对SGEMM只约4倍headroom时还能加速，要求自研复用内核比“六次完整oneMKL BF16调用”更有效。这在逻辑上并不矛盾，因为raw基准是另一个实现，且不能共享同样的跨产品输入驻留；但仅靠14/24加载减少也不能数学保证整机获益，必须有自研组件有效吞吐及端到端实测。

热tile、流式tile、完整BF16 GEMM、有效高精度GEMM是四种不同边界。峰值除以Np只能做同工作定义下的粗成本预算，不是完整API必达目标；tile逻辑载荷字节也不是DRAM流量。归一化两阶段条形图只能说明占比，不能确定瓶颈是AMX、缓存、重建或NUMA。

## 7. 硬件、MKL和计时可比性

论文平台见§7.1 pp.17–18：8462Y+双路、64物理核心线程、Intel编译器/OpenMP、固定campaign频率策略。当前仓库报告是8454H双路、GCC/GNU OpenMP、Ubuntu、powersave且频率不固定。即便两个实验都请求64线程，也不能推出实际核映射、NUMA页放置、调度成本和频率相同。不能用硬件名称差异单独解释全部结果，更不能据同属一代CPU直接要求性能相等。

论文总时间包含预处理和重建，而MKL按native routine计时（§8.3，p.21）。所以“自研端到端 vs MKL GEMM调用”本身是论文想回答的问题，不应笼统说这种比较天然不公平。需要额外隔离的是本项目接口增加的验证、内存池、提交/拷贝、错误事务语义、每线程tile配置等是否进入时间，与作者接口是否相同。库调用前后统一墙钟是应用层主要指标；阶段profile则用于解释，不应替换headline计时。

同版oneMKL不能证明相同内核dispatch、同线程运行时或同归约顺序。MKL verbose可验证库宣称的版本/线程数/ISA能力，但不等于证明某次内核执行了指定指令；若讨论实际指令路径，需更直接的跟踪或反汇编证据。数值参考也要保留MKL误差，不能将MKL作为精确实数AB。

对既有结果，最稳妥结论是：FP32经验误差相近；FP64同预算的误差显著偏大；本地大规模端到端多数未复现论文speedup。全66配置覆盖完成描述的是测量覆盖，不能改变这些结论。

- FP64 max/shift的实际全矩阵、panel或row/column作用域；带符号与否只能依据式(14)按正shift读，作者机器实现没有可核对代码（§4.3，p.10；§6，pp.14–17）。
- 完整BK/K32/product循环嵌套、同对角线内顺序、完整FP32舍入树（§4，pp.8–11；§6，pp.15–17）。
- 每worker AMX配置/许可、缓冲区生命周期和分配时机；跨调用重用；首次触页和NUMA策略（§6.3、§7.4，pp.16–19）。
- 具体频率值、turbo/功率限制、内存配置、CPU拓扑映射、MKL动态线程开关；compacting之外的绑定细节（§7.1，pp.17–18）。
- 各配置原始十次时间、方差、精确图9数值；补充输入族的逐阶精度；异常边界覆盖（§7–8，pp.17–25）。
- 图中GFLOPS是否笔误及原始秒数（§8.1–8.3，pp.20–24）。

缺项应形成可发送作者的明确问题，不应用反向调参把它们隐藏。

## 9. 最有价值的下一步验证，不修改生产算法

| 优先级 | 验证 | 判别力/停止条件 |
|---|---|---|
| 1 | 使用现有导出切片，逐片验证公共格距、整数范围≤256、BK256 dot可精确表示；同时记录FP32组件对高精度dot的实际误差 | 若成立，停止把FP32地板当主因，集中研究分解/截断；若不成立，定位尺度作用域或边界 |
| 1 | 多seed、两个以上小N，固定literal rho45与已存在signed-shift假设，记录每层max、v、正负格距、terminal residual、四档tail | 检查误差倍率是否稳健反映公式差异；全部作为独立诊断，不更换默认公式 |
| 1 | 建立作者询问包：p.10公式截图、同输入切片/误差谱、BK重建伪码、单位反算 | 请确认shift符号/rho/作用域/归约边界、表4生成方式与原始时间；没有答复也保留可复核差距 |
| 2 | 在同批、同核映射、同频率观察及等待策略下交替测本项目完整API和MKL native call，保存每次样本 | 消除跨批时序漂移；报告方差与API附加成本，不只拿各批最优值 |
| 2 | 使用已有phase数据核算split/pack、复制、AMX、widen/add、commit时间与工作量；需要时设计独立instrumented诊断 | 若阶段计时无法闭合总时间，先修证据口径再做瓶颈结论；不把去重建实验当有效算法 |
| 3 | 原协议只需64核；额外单socket/绑定/页放置对照作为性能诊断 | 判别NUMA/并行成本，不把扩展实验算成作者协议的原始结果 |

审查建议优先完成前两项数值验证，而不是再做一轮大范围分块搜索。它们能直接回答“Table4差距究竟来自哪个数学阶段”，也能避免以性能优化掩盖数值方法差异。若只允许一个最小实验，应选择同输入的分片格距和selected-products高精度分解，复用已导出的数据即可，不需要修改实现。
