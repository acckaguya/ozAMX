# V4 搜索记录

## 固定起点

V3 的论文对齐补测已于 2026-10-14 完成：40 项主表、18 项线程扩展、8 项 raw BF16，共 66 项，各 10 次计时。补充冻结包为 `bench/8454h/versions/v3_paper_release/`，447 个 manifest 项逐一校验通过；manifest SHA-256 为 `cc0e6bab8b5f0d7785988e551d3de2a38ac056e366530b749c06d6394772e0d1`。静态库仍为 `73f0764610072b05a3e50afb8ce312fe6b717c361efef7b94e52f20bde63b42c`，旧 V3 release 不变。详见 [论文对齐报告](8454H_V3_PAPER_ALIGNMENT.md)。

本轮只在独立实验树中修改代码。所有构建、数值计算、性能测试持有 `/tmp/ozamx-perf.lock`；固定 64 个物理核、CPU 0–63、线程绑定、输入 seed 和 2 GiB 工作区缓存。完整 API 是选择实现的性能口径，阶段 profile 用于定位瓶颈。计时样本全部保留，共享主机漂移由同批 V3 对照观察。

## 循环 1：检查重建成本

假设：逐次非有限检查、FP32→FP64 转换和 C 重建访存占用了显著时间。

实现：在现有实际打包布局上分别保留控制路径、取消 FP32 逐次检查的诊断、去掉重建的诊断，以及延后 FP32 检查的候选。两端使用冻结 V3 库作对照。

验证：control 和延后检查各通过 3 项 CTest、18 项完整输出字节和异常/别名比较。6 组、90 个配置，各有 5 次原始计时。CSV 漏末引号的输出问题已保留原文件，独立修复副本逐项核对 checkpoint；后续 driver 修正格式，原运行源码快照保留。

分析：N=8192、FP64 p21 去掉重建后的 compute 约 446 ms，控制约 551 ms，缩短约 19%。这条诊断不生成有效 GEMM 输出，不能发布为加速实现。延后 FP32 检查没有显示稳定收益。首尾对照有漂移，尤其部分 FP32/小矩阵时段，不能只用首个较慢控制宣称提升。详见 [诊断报告](8454H_V4_DIAGNOSTIC_RESULTS.md)。

修改：扩大重建 batch、宏块及打包布局空间，继续寻找产品内核在真实地址上的差距。

## 循环 2：确认现时局部上限

重新执行 57 个校准配置，每项 1 次预热、3 次计时，共 228 行。检查全部通过。64 核 AMX 热寄存器中位峰值为 161.018 TFLOP/s；产品内核 P21 无重建约 123.239 TFLOP/s，含重建约 86.306 AMX 等效 TFLOP/s。与前轮局部上限基本一致。实际大矩阵无重建路径约 52 TFLOP/s，仍有显著差距。

这些值分别对应寄存器驻留、小工作集和完整实际布局，不能混合解释为同一个 GEMM 上限，也不是测得的 DRAM 流量。详见 [新校准报告](8454H_V4_ROOFLINE_CALIBRATION.md)。

## 循环 3：INT8 整数累加原型

假设：INT32 保持整个 K 的和，最后只重建一次，可能减少反复转换与 C 访存。

实现：8 位片、36 个有符号 INT8 产品，手写 AMX 汇编，AVX-512 并行扫描/打包，8 个整数对角线和最终 INT128 舍入。修复 tilecfg 字段偏移和最高位 +64 的 carry 处理；独立 scalar/SIMD probe 通过。

验证/分析：16 个数值 case 全部执行，异常与别名保护通过，但全局定点编码在 K=1、稀疏和指数互相抵消的动态范围输入上没有通过预设精度门。动态案例 e_scaled≈0.291。保留全部失败；不放宽门槛，没有运行性能矩阵，没有加入公共 dispatch。详见 [INT8 实验报告](8454H_V4_INT8_EXPERIMENT.md) 和 [成本模型](8454H_V4_COST_MODEL.md)。

修改：当前通用路径继续 BF16 搜索；INT8 的后续需要输入范围或编码/校正方案的独立精度设计。

## 循环 4：扩大保持数值语义的搜索

第一阶段 30 组组合，范围为 FP64 重建 batch 2/4/8/12/21、CBM 64/128/256、CBN auto/128/256/512/1024。BK=256 与产品加法顺序不变。候选先过 CTest 和快速字节门，再测 N=8192、FP32 与四档 FP64，各 3 次计时；每 5 个候选插入固定 V3 对照，首尾对照各 7 次。后续再比较 padding×tile 加载方式 6 组，对胜者做完整字节门和 7 次匹配复核。

第一屏已完成：29 组候选各有 5 个 workload、每项 3 次计时，均通过快速字节门和 CTest。另一组 CBM=256、CBN=1024 的候选在默认 OpenMP 栈下 SIGSEGV；同一二进制扩大栈后的通过仅作为诊断，未计入有效候选。driver 参数、CSV 状态验证和默认配置目录重名等运行问题的失败日志与续跑来源均保留。结果在 `search_runs/screen_20261014_20261014T094029Z_retry2/`。

初筛留下 batch=2、CBM=256、CBN=256/512 两个几何配置。评分使用候选与初始控制的 MKL/API 比值，仅供筛选：其间 V3 五个 workload 的平均 API 时间从约 0.378 s 漂移至最终约 0.557 s。因此该评分不能作为发布加速比。后续对 CBM=256、CBN=256 的 padding×tile-load 组合完成六组筛选；六组均通过 3 项 CTest、6 项快速字节门，并各有 N=8192 五 workload、三次原始计时。p0/h1 的额外 20 项完整字节门通过。布局组合没有显示稳定的跨 workload 胜出；详细 API 与阶段数据、V3 对照限制和成本模型复核见 [布局复核报告](8454H_V4_LAYOUT_RESULTS.md)。最终候选仍须使用匹配 V3 调用的复核结果判断。

## 循环 5：打包间隔与分量地址轮转

FP64 实际 slab 为 16 KiB，一个含八个 slab 的面板为 128 KiB；先前的 512 KiB 步长假设不适用于当前布局。保持每个 K32 tile 和汇编 K 步长不变，测试 11 组 A/B 间隔以及 5 组分量 slab 地址轮转，共 16 组。全部通过完整 20 项数值门与 CTest，每组四档 FP64、各三次计时。

间隔没有显示稳定收益，部分配置完整 API 额外开销显著上升。零间隔的轮转在不同预算上有小幅变化，尚不足以判定胜者。保留所有样本，修正独立容量分析中把产品数误当存储分片数的公式；原元数据不覆盖。普通 4 KiB 页的虚拟地址步长不能证明物理 L2 组冲突，本次没有 PMU miss 数据。详见 [布局实验报告](8454H_V4_PACKED_LAYOUT_RESULTS.md)。

## 循环 6：手写 AVX-512 重建

假设：在不改变每个输出的产品加法顺序的前提下，交错八条 FP64 累加链可以隐藏转换与加法延迟。新汇编一次处理两行，每个产品先转换八个向量，再更新八个 double 累加器；仅用于已有最终非有限检查的 Late64 路径。

直接 probe 覆盖五种行跨度、六种 batch 数、有限值、特殊值、padding 和 SysV 保留寄存器。batch=2/8/12/21 的开启与关闭共八组均通过完整 GEMM 字节门与 CTest。对象文件重定位也确认开启版本实际调用新汇编，关闭版本无该调用。八组计时已完成，batch 2/8 的部分收益仅几个百分点，batch 12/21 有明显慢样本；所有样本与首尾 V3 控制保留，尚未宣告稳定性能提升。详见 [汇编重建报告](8454H_V4_RECON_ILP_RESULTS.md)。只读冻结包中的可执行文件权限导致一次 control 启动失败，随后用同一 driver 和冻结库重新构建控制，未修改冻结包或重跑已通过的数值门。

## 循环 7：宏块上的 padding 与加载提示

在初筛的 batch=2、CBM=256、CBN=256 上补做 padding=0/64/128 B 与 TILELOAD/TILELOADT1 的六组组合。6/6 通过 CTest 和快速六项门，五个 workload、每项三次计时的 CSV/checkpoint 及身份核验完整。最有希望的 padding=0/TILELOADT1 还通过了完整 20 项字节门。

相对同批 padding=64/TILELOADT1，padding=0/TILELOADT1 的 FP32 API 约缩短 10%，p15/p21 变化很小，但 p6/p10 分别慢约 8%/13%；五项几何平均 API 比为 1.014（更慢）。其它组合也没有稳定的总体收益。后续几何复核保留原 padding=64/TILELOADT1，不凭单个预算的快样本改变默认值。

## 循环 8：页面对齐和 THP

只读确认当前大工作区使用 `posix_memalign(...,64,bytes)`，未请求 `MADV_HUGEPAGE`，本机 THP 模式为 `madvise`。新实验仅比较大于等于 2 MiB 的分配：4 KiB/2 MiB 对齐 × 大页提示开关，共四组；计算几何、加法顺序和生产 mode 0 保持一致。保留 std::free、按逻辑大小缓存和分配失败语义；hint 只作用于当前分配拥有的完整页，失败不改变数值 API。

四组完整数值门与 API profile 均完成，并在计时外收集 smaps，区分 hint 成功与实际 AnonHugePages。两组 hint 确实获得大页。随后二十项、各十一对的交替复核仍有明显均值/中位数和位置效应分歧，没有采用 allocator 变化。详见 [page screen](8454H_V4_PAGE_LAYOUT_RESULTS.md) 与 [page matched](8454H_V4_PAGE_MATCHED_RESULTS.md)。没有测得 TLB miss，因此页面翻译瓶颈仍是待验证假设。Linux 官方技术说明及下载身份保存到 third_party，未修改全局 THP、NUMA 或频率设置。

## 循环 9：AMX 加载与点积分组

手写两种 FP64 产品内核调度：分别按 B 列和 A 行分组，把另一个 tile 加载排到两条独立点积之间。同样四次 tile 加载、四次点积，不改变每个输出的 K32 累加次序。控制编译出的库与冻结 V3 字节一致，两个候选的反汇编指令序列互不相同。

两组各通过 CTest 和完整二十项门；N=8192 四预算各十一对的默认等待策略交替测试亦逐字节一致。预算之间有取舍，无稳定整体收益，未采用。详见 [AMX 调度报告](8454H_V4_KERNEL_SCHEDULE_RESULTS.md)。本轮共 65 组有计时的参数配置；另有两种精简自适应候选及多批独立复核。

## 最终确认的口径

顺序运行整组候选容易受到共享主机漂移影响。最终复核采用两个持续存在、分别静态链接候选库与冻结 V3 库的进程，由父进程逐次交替调用；计时包含完整公开 API，预热与输入生成在计时外。初批两个 OpenMP 团队统一使用 PASSIVE 等待并记录环境差异；随后恢复默认等待策略，并在 API 外等 20 ms，检验初批收益能否迁移。保留每次调用顺序、原始阶段时间、完整输出比较和库/源码身份。

最终当前主代码为 0.4.0，仅在默认缓存块参数、FP32 M/N 处于 4096–8192 且 K 处于 4096–8192 的范围采用 256×256 宏块。完整 23 项门、OpenMP/no-OpenMP 验证、实际主代码交替复核和 ten-row oneMKL 补测全部完成。N=4096/8192 FP32 平均完整 API 耗时减少约 4.1%/7.6%；没有将 FP64 候选或 N=16384 RC1 实验泛化到默认实现。完整结论及硬件差距见 [本轮总报告](8454H_V4_ROUND_RESULTS.md)。
