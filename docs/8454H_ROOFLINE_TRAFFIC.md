# 8454H Roofline Traffic Ledger: Immutable V2 and Adaptive V3

This roofline pass turns immutable V2 source into explicit work and byte counts, then adds a separate adaptive V3 Batch2 model. It is intended to guide the next search by identifying plausible stage costs. It does not claim to measure cache misses or physical DRAM traffic. The machine's older platform CSV and `perf paranoid=4` counters are unavailable; physical cache/DRAM conclusions are scenarios or estimates. Immutable V2 source snapshots are under `bench/8454h/versions/v2/`.

The machine-readable formulas and source references are in [traffic_model.json](../bench/8454h/roofline/traffic_model.json). The measurements available for calibration are the 20 rows in [full_production.csv](../bench/8454h/mkl_production/full_production.csv): four square sizes (256, 1024, 4096, 8192), five product budgets, 64 threads, and five repetitions. Each row separates split, pack, and compute/reconstruct phase time, but the last phase still combines AMX work, SIMD reconstruction, and output copies.

## Work has two different counts

For a matrix product, report useful effective work as `Weff = 2MNK` FLOPs. The AMX BF16 engines execute the component-product expansion, so useful component work is `Wamx,useful = 2MNK × p`, where `p` is the number of independent BF16 product pairs. Keep those columns separate: `Weff` undercounts AMX component-product work by a factor of `p`. Issued padded work is `Wamx,executed = 2MpNpKp32p`, with `Mp=ceil(M/32)32`, `Np=ceil(N/32)32`, and `Kp32=ceil(K/32)32`.

FP32 uses six pairs: `(A0,B0)`, `(A0,B1)`, `(A0,B2)`, `(A1,B0)`, `(A1,B1)`, `(A2,B0)`. The six-product assembly chain issues 24 `TDPBF16PS` instructions for each K32 step. FP64 uses the independent pairs on its selected triangular diagonals: p6 stores 3 slices and uses 6 pairs; p10 stores 4 and uses 10 pairs; p15 stores 5 and uses 15 pairs; p21 stores 6 and uses 21 pairs. Each pair calls the single-product assembly kernel and issues four TDP instructions per K32. Exact counts are `24 ceil(M/32)ceil(N/32)ceil(K/32)` for FP32 and `4p ceil(M/32)ceil(N/32)ceil(K/32)` for FP64. One TDP instruction represents 16,384 BF16 component FLOPs. Useful `2MNKp` differs from issued work when M, N, or K needs padding.

AMX and AVX-512 must use separate rooflines. For each stage, use `t >= max(W/P, Q/B)` with the stage's own compute ceiling and bandwidth boundary. Here `P_AMX` applies to BF16 TDP operations and `P_SIMD` to projection/reconstruction operations. Source and the current phase timer do not show whether AMX and SIMD overlap, so do not combine their operation counts and divide by one peak. The practical stage list is projection/split, panel packing, AMX products, SIMD accumulation/reconstruction, result/C copies, and dispatch/allocation/thread/tile-state overhead.

## Instruction payload and physical traffic have different boundaries

The assembly loads 16 rows of 64 bytes per tile instruction, or 1024 logical bytes. Let `tileMN=ceil(M/32)ceil(N/32)`. The FP32 six-product kernel loads 14 operand tiles for every output 32×32 microtile and K32 step: six A tiles and six B tiles cover the six pairs, while two operand tiles are loaded a second time. Total logical tileload payload is `14×1024×tileMN×ceil(K/32)` bytes. For FP64, one independent product loads four tiles, or 4,096 bytes per K32; a budget with `p` products uses `4p×1024×tileMN×ceil(K/32)` bytes. These are instruction-level payloads. Neighboring output tiles can reuse panel bytes from L1/L2 or lower levels, but that does not erase the tileload instructions. Conversely, repeated payloads need not reach DRAM if the cache supplies them.

Each kernel call stores four 16×16 FP32 accumulator tiles: 4,096 bytes for a 32×32 microtile. There is one call per 256-wide K block in FP32 and `p` calls per K block in FP64. Including padded output microtiles, this gives `4096×tileMN×ceil(K/256)` logical stored bytes for FP32 and `4096p×tileMN×ceil(K/256)` for FP64. These are explicit AMX tile stores, separate from SIMD accumulator traffic.

The cold/materialized traffic scenario counts source reads, explicit projection and packing streams, panel materialization, and result/C copies. Here `S=MK+KN` is the scalar source-element count before dtype sizing. For FP32, a general split-plus-pack path touches `4S` source bytes, `6S` dense slice write/read bytes, and writes `6Ppanel` panel bytes; aligned direct projection writes `6S` panel bytes. FP32 stores three BF16 slices at 2 bytes each. For FP64 depth `d`, the general path writes and rereads `2dS` dense slices and writes `2dPpanel` panel bytes; aligned direct projection writes `2dS` panel bytes. `Ppanel` is the padded A+B BF16 element count for one slice; each element occupies 2 bytes. Result/C copy streams are four element transfers per output: `16MN` bytes for FP32 and `32MN` for FP64, since the FP64 result and caller C are both double. These are logical/materialized scenario counts, neither a strict DRAM lower bound nor a measurement. Warm-cache repeated calls can produce much lower physical DRAM traffic, especially when panels remain resident. These scenario counts do not replace tileload or SIMD instruction traffic.

## Projection and packing streams

The general FP32 path reads source matrices once (`4(MK+KN)`), writes three dense BF16 slices (`6S`), then reads those slices for packing (`6S`) and writes `6Ppanel` bytes of panel layout. The aligned direct path is enabled when `min(M,N)>=1024` and M, N, K are multiples of 256; it emits three 2-byte slices directly into panel layout (`6S` bytes) and removes the dense intermediate slice read/write. The current direct path is already an example of a model-driven candidate that should be extended carefully around tails.

FP64 always evaluates all six projection rounds to preserve the six-component validation/residual chain. Product budget only limits persistent slice storage and AMX products. For `S=MK+KN`, both paths write the initial `8S` double residual. In the general split path, each of six rounds reads residual once for max collection, reads it again for projection, then writes the updated residual: 152S logical residual-array bytes total. The general path also writes `2dS` dense BF16 slice bytes, reads `2dS` during pack, and writes padded panels. The aligned direct path computes next-max during projection update, so each round has one residual read and one write; including initialization, that is 104S logical bytes. Source reads are counted separately. Both paths retain six projection rounds. These logical reads/writes may be served from cache and are not physical DRAM counts.

Panel packing pads to 256×256 panels. For A and B together, one slice allocates `Ppanel = ceil(M/256)ceil(K/256)65536 + ceil(K/256)ceil(N/256)65536` BF16 elements. Thus `6Ppanel` bytes is the FP32 panel-write total for three stored slices across the aggregate A+B one-slice count; do not multiply by A/B again. A dense-slice path reads only useful elements but writes padded panels, including zero padding. Aligned shapes have no padding. Small or misaligned shapes therefore pay a potentially material panel-write overhead and still use the separate split then pack path.

## Reconstruction, output, and RFO

For FP32, each 32×32 product microtile accumulation reads the 4,096-byte FP32 micro result and reads/writes 4,096 bytes of the FP32 output block: 12 logical bytes per padded output scalar per K256 chunk. For FP64, each product reads the same FP32 micro result (4,096 bytes), converts its values to double, and reads/writes 8,192-byte double output blocks: 20 logical bytes per padded output scalar per independent product. With `r=ceil(K/256)`, totals are `12MpNp r` bytes for FP32 and `20pMpNp r` for FP64. FP32 performs `MpNp r` SIMD additions; FP64 performs `pMpNp r` conversions and the same number of ordered additions. The p=21 long-K case is especially sensitive to repeatedly loading and storing the double accumulator. The long-K path defers finite checks, but still performs those accumulation updates.

After a cache block is accumulated, V2 copies valid rows into a dense private result buffer and then copies that buffer to caller C. Those stages account for 16MN logical bytes in FP32 and 32MN in FP64. It also zeros a full private cache block per output block, including edge padding: `sizeof(T) × cb² × ceil(M/cb) × ceil(N/cb)`, with `cb=32` below 1024 and `cb=128` otherwise. A cold, single-pass temporal-store scenario may incur about one cache-line read-for-ownership per cold line written. This is a scenario estimate, not a physical upper bound: repeated eviction, coherence transfers, and false sharing can cause additional ownership traffic. No RFO amount is added to the logical-byte totals.

## Model-driven candidates for the next search

Use stage times and the traffic ledger to choose a small candidate set:

1. Extend fused projection-to-panel preparation to divisible matrices plus a tile-buffered tail path. The traffic hypothesis is removal of dense-slice writes and rereads: 12S bytes for FP32 (6S write + 6S reread), or 4dS for FP64, plus fewer API/allocation costs. Preserve all six FP64 projections.
2. Test blocked residual streaming for FP64. The hypothesis is fewer residual round trips or better cache residency while retaining the global max/sigma barriers and all six rounds. Use split time plus cache/DRAM counters once available.
3. Reduce repeated FP64 output-block loads/stores by holding a larger output tile in registers or L1 across multiple products. The current ledger charges 20p bytes per scalar output per K256 block. Preserve the p product pairs and component accumulation order.
4. Compare K/product-major scheduling against current scheduling for panel reuse. This cannot reduce exact tileload instruction bytes; it may improve the cache level that serves them. Require L1/L2 counters to validate the hypothesis.
5. Select output cache block from a per-thread working-set model, including the private block (`4cb²` bytes FP32 or `8cb²` FP64), zeroing and copies. Consider 32/64/128/256 as hypotheses, not as blind cache-macro reruns; track cache misses, RFO/writeback, and phase time.

The CSV can calibrate effective phase ceilings and show which sizes/budgets spend time in preprocessing versus the combined compute/reconstruct phase. Its MKL timing covers GEMM only, while our API time includes preparation, packing, and output copies; whole-API speedups are not a compute-only roofline comparison. For physical DRAM bandwidth and cache-level reuse, the source gives cold/materialized scenario estimates, while the CSV has no cache or DRAM counters to measure actual traffic. Hardware counters are needed to compare those scenarios with physical transfers.


## Adaptive V3 Batch2 addendum

The V3 model is separate from the immutable V2 ledger above. Its large-shape dispatch activates when `min(M,N)>=4096`; it uses a 128-row output block and 512 columns for FP32 and FP64 depths up to four, or 256 columns for FP64 depths five and six. The per-row accumulator stride includes a 64-byte pad. AMX pair counts, tileloads/stores, product ordering, and SIMD conversion/add counts remain as in V2.

For Wide FP64, V3 processes two products per double-accumulator round. It still reads each product's FP32 micro result and performs all `pMpNp r` conversions and ordered additions. The number of double block read/write rounds is `ceil(p/2)` rather than `p`, so logical reconstruction traffic becomes `(4p + 16ceil(p/2))MpNp r` bytes, compared with V2's `20pMpNp r`. Scratch capacity rises from one 32×32 float microtile (4 KiB) to two (8 KiB) per worker. These are logical instruction demands, not measured cache or DRAM traffic. The V3 production build and strict full-buffer gate are recorded in `bench/8454h/roofline/production_validation.json` and `bench/8454h/roofline/binary_gate.json`.
