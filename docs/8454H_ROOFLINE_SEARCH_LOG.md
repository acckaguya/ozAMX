## Recording requirements

For every measurement, record host and microcode identity, compiler and flags, affinity and thread settings, frequency policy, lock status, counters and their units, counter multiplexing, repetitions, uncertainty, command, raw artifact paths, and SHA-256 values. Distinguish measured ceilings from vendor specifications and derived values from raw readings. Keep V2 as the comparison baseline and retain each candidate's complete validation evidence. Do not change the production source as part of the baseline freeze.

The batch64 run used `/tmp/ozamx-perf.lock` for the entire eight-process sequence. It records software `getrusage` counters, not hardware cache/DRAM counters. Frequency policy was not controlled or sampled. [comparison.json](../bench/8454h/roofline/search_batch64/comparison.json) includes per-run and pooled medians for compute phase, profile total, full API wall, page faults, context switches and CPU time. The eight raw CSVs preserve warmups, all five measured reps, and driver summaries; the medians use only the five explicitly labeled rep rows and do not trim outliers. Batch=1 is an isolated control build with helper dispatch, not the frozen V2 library or binary.

## Pad, THP, rectangular and adaptive scout cycle

Four additional search families are summarized offline in [`search_pad/`](../bench/8454h/roofline/search_pad/), [`search_thp/`](../bench/8454h/roofline/search_thp/), [`search_rect/`](../bench/8454h/roofline/search_rect/), and [`search_adaptive/`](../bench/8454h/roofline/search_adaptive/). Each directory now has a `summary.json` retaining every timed repetition, process-level medians and configuration aggregates, plus `metadata.json` with CSV and source/library/binary hashes, CMake options, build identities, environment, and pass ordering. [`summarize_searches.py`](../bench/8454h/roofline/summarize_searches.py) regenerates these files without running a benchmark. [`search_commands.md`](../bench/8454h/roofline/search_commands.md) records reconstructed invocation templates; exact original shell transcripts were not preserved.

The common scout environment was 64 workers on CPUs 0–63, close core binding, dynamic OpenMP disabled, and a 2 GiB workspace cache. Pad and rectangular sweeps used 5 timed repetitions for nine configurations across N=1024/4096/8192; THP used the same nine configurations in an off/on/off/on/off control sequence. Adaptive used 7 timed repetitions for 20 configurations across N=1024/2048/4096/8192. Statistics use `record=rep` only, compute each process median first, then compare medians across repeated processes. Raw reps and flagged outliers remain present; no sample was trimmed.

These aggregate percentages are medians across the nine per-configuration process-median changes in measured API wall time (`wall_s`); `total_s` (profiled split+pack+compute) is retained as a secondary metric in the JSON. They are not an across-size speedup or a confidence interval. Given the limited repetitions, hardware-noise exposure and multiple knobs, they are scout rankings only; no production choice follows from them. THP's `smaps` probes show `AnonHugePages` changing from 0 KiB for hint-off to 497,664 KiB during hint-on probe samples. That confirms huge-page backing in the probe but does not establish a workload speedup or a measured bandwidth change.

The adaptive scout showed its clearest gains at N≥4096: across N=8192, median API wall changes were −15.69% (FP32/p6), −15.35% (FP64/p6), −12.63% (p10), −6.39% (p15), and −7.84% (p21). At N=4096 the corresponding shifts were −4.13%, −1.16%, −5.48%, −6.19%, and −10.56%. These are medians of process medians from three frozen and two candidate processes, with all seven reps retained per process. At N=2048/p21, the merged candidate median regressed +15.84%; one candidate process had a median around 15.64 ms while the other was around 11.80 ms, versus frozen process medians around 11.78–12.88 ms. This discrepancy remains in the raw data and must not be discarded as noise. The current V3 source includes the adaptive large-shape geometry, and the [12-case full-output binary gate](../bench/8454h/roofline/binary_gate.json) passed byte-for-byte. The later production validation recorded 147,456 exact component stores and 730 exact reconstructions, with zero mismatches; the current V3 oneMKL comparison is recorded in the [results report](8454H_ROOFLINE_RESULTS.md).

The aggregation keeps the public API `wall_s` primary and profiled `total_s` secondary. The call path includes setup and teardown, while the reported profile stages do not account for every API cost, so small differences between those measures are expected. No adaptive policy was enabled for N<4096; the small-size production geometry remains unchanged. Shape-dependent improvements at N≥4096 are a reason to run the full validation/gate, not to declare a speedup before it passes.

The initial CTest invocation omitted unbuilt alias/late-path executables, which appeared as `NotRun`; after all targets were built, the complete suite passed. This was a test-invocation gap, not a numerical benchmark failure.

One Astra review of the roofline approach recommended keeping compute and memory/reconstruction stages separated, treating logical byte counts as distinct from physical traffic, and recording batch footprint, layout and NUMA placement alongside performance. It also suggested investigating a 16×32 tile pair, but the added B-panel load cost was not justified and that layout was not implemented. These are experiment-design notes, not measured conclusions. The saved 8454H tileload/triad probes still provide logical payload-rate references only; physical per-level traffic awaits PMU measurements.
