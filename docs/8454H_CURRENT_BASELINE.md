# Xeon 8454H current machine baseline

This is the self-contained measurement baseline for the shared Xeon Platinum 8454H host. The current source is version 0.4.0 with the bounded FP32 CompactWide change described below. The V3 measurements and frozen artifacts remain historical references. Earlier matched-release numbers in [8454H_PERFORMANCE_BASELINE.md](8454H_PERFORMANCE_BASELINE.md) remain historical snapshots; this page does not merge separate campaigns.

## Machine and run conditions

The machine is a dual-socket Intel Xeon Platinum 8454H: 2 sockets × 32 physical cores, 2-way SMT, 128 online logical CPUs total. It has two NUMA nodes, each with 32 physical cores and their SMT siblings. Benchmarks pin to CPUs 0–63: CPUs 0–31 are node 0 and 32–63 are node 1. This is one logical CPU from each physical core, spanning both sockets. The captured cache topology is 3 MiB L1d and 2 MiB L1i across 64 instances, 128 MiB L2 across 64 instances, and 165 MiB L3 across two instances. The CPU reports AVX-512, AVX512-BF16, AMX-TILE, AMX-BF16 and AMX-INT8.

The OS is Ubuntu 22.04.5 LTS, Linux 5.15.0-161-generic. The frequency policy reports 800–3400 MHz; the governor is `powersave`, and frequency is not pinned. The paper campaign's visible cgroup and parent `memory.max` values were unlimited. `perf_event_paranoid` was 4, so no PMU/perf counters were collected. The local campaigns held `/tmp/ozamx-perf.lock` to serialize their own CPU-heavy runs, but this is a shared, nonexclusive host: unrelated workloads may still contend for cores, memory bandwidth or frequency headroom. Do not interpret the timing variance as isolated-host variance.

The 2026-10-14 calibration and paper campaign used GNU GCC 11.4, GNU OpenMP, and `taskset -c 0-63`, with `OMP_NUM_THREADS=64`, `OMP_PLACES=cores`, `OMP_PROC_BIND=close`, and `OMP_DYNAMIC=FALSE`. oneMKL was 2026.1, GNU threading layer, with `MKL_NUM_THREADS=64` and `MKL_DYNAMIC=FALSE`. Inputs in the V3 paper campaign were generated by the caller thread with `std::mt19937_64`, uniform on [-1,1], base seed 260904 plus N; caller allocation and input generation were outside the API timer. There was no explicit NUMA interleave policy, so these caller-filled input arrays were first-touched by the caller. The V3 workspace cache limit was 2 GiB (`OZAMX_WORKSPACE_CACHE_BYTES=2147483648`). No system governor or frequency settings were changed.

The measured frozen V3 static library SHA-256 is `73f0764610072b05a3e50afb8ce312fe6b717c361efef7b94e52f20bde63b42c`. The paper campaign benchmark and raw-BF16 driver source hashes are `acf8b0ba205314205ab1bb3562258c77c198a0c2a7b9bf214c936cd652bb33a6` and `83616f51bd2ead1a04fa0af08972f5e689a6c14164f8a26548cc94aaae3a837f`. The oneMKL runtime SHA-256 is `b2ff0e31d7cd18c91813d8f6500f37665597d89de22649d90687aa6bf7bd2c0f`. The paper used a different machine and environment: dual Xeon Platinum 8462Y+, Rocky Linux 9.3, Intel compiler/OpenMP. Thus local measurements are protocol-aligned in important respects, but not platform/toolchain-identical.

## Hot AMX and small-working-set kernel calibration

The 2026-10-14 roofline calibration ran 57 configurations, each with a warmup and three timed samples. Each timed kernel window ran for at least 80 ms. These are isolated-kernel measurements, not GEMM API timings. `AMX register-hot` keeps tiles resident and repeatedly issues four independent BF16-to-FP32 TDP operations; it performs no matrix traversal or reconstruction. Its 64-thread result is a median of the three observed rates, with sample standard deviation shown in parentheses.

| Kernel | Per-worker input footprint | 64-thread throughput (TFLOP/s, median; sample SD) | Interpretation |
|---|---:|---:|---|
| AMX register-hot | 4 KiB | 161.018 (0.055) | Register-resident TDP ceiling; no input streaming or reconstruction |
| FP32 six-component, product-only | 96 KiB | 155.550 (0.244) | Six component products, no reconstruct |
| FP32 six-component, mixed with reconstruction | 96 KiB | 151.738 (1.073) | Six component products plus FP32 reconstruction mix |
| FP64 p6, product-only | 192 KiB | 121.593 (0.400) | Six-product component workload, no reconstruction |
| FP64 p6, mixed with reconstruction | 192 KiB | 84.423 (0.620) | Product work interleaved with FP64 reconstruction |
| FP64 p21, product-only | 192 KiB | 123.239 (0.389) | Twenty-one-product component workload, no reconstruction |
| FP64 p21, mixed with reconstruction | 192 KiB | 86.306 (0.296) | Product work interleaved with FP64 reconstruction |

The mixed rows deliberately combine product and reconstruction in a hot, repeated working set; they are useful component ceilings and cost comparisons. They do not include complete API dispatch, caller input placement, normal matrix sizes, or all production overhead. The calibration reports logical bytes from the explicit kernel model, not PMU-measured cache or DRAM traffic. See the archived [raw calibration](../bench/8454h/roofline_v4/calibration_20261014/raw/kernels.csv), [offline analysis](../bench/8454h/roofline_v4/calibration_20261014/analysis.json), [environment](../bench/8454h/roofline_v4/calibration_20261014/environment.json), and [calibration protocol](../bench/8454h/roofline_v4/calibration_20261014/README.md).

The raw per-configuration CSVs, ten-sample checkpoints, timestamps, commands, source/runtime identities and hardware snapshots are retained in [`bench/8454h/v3_paper_alignment/`](../bench/8454h/v3_paper_alignment/). The complete 40-case accuracy comparison and paper ratios are in [8454H_V3_PAPER_ALIGNMENT.md](8454H_V3_PAPER_ALIGNMENT.md) and [`analysis.json`](../bench/8454h/v3_paper_alignment/analysis.json). V3 rows marked `status=ok` report successful execution; they do **not** establish paper-level precision. In particular, FP64 errors measured in this local campaign are above the paper values: median measured/paper eF ratios are 5.701× (p6), 11.146× (p10), 21.916× (p15), and 8.207× (p21); median e_scaled ratios are 5.563×, 10.835×, 21.856×, and 4.404×. These ratios are observations, not acceptance thresholds. The high-precision diagnostic sampled for large N is supplementary and does not replace the full-matrix oneMKL comparison.

This V3 run was a separate campaign from the roofline calibration and from the raw oneMKL headroom table. Although each used the same host and serialized its own CPU-intensive work under the lock, they occurred at different times and are not presented as simultaneous or matched measurements. The campaign is also subject to shared-host contention and powersave frequency behavior. API wall samples include the full V3 call (including decomposition, packing, compute, reconstruction, dispatch and teardown); per-thread tile configuration remains within compute for this implementation. The paper excludes permission/setup outside timing but does not specify its worker tile-configuration mechanics.

## Version 0.4.0: bounded FP32 result

The adopted source uses a 256×256 FP32 macroblock only with the default `CACHE_BLOCK=128`, M/N both at least 4096 and at most 8192, and K between 4096 and 8192. Other domains use the existing paths. The validated OpenMP archive is `7adcc98996d5a88aa21f74038a42710a28496cf601f2127c016b8e8687801b68`; no-OpenMP archive is `c3baf4364d7dbf7b22e12a7f2662b7c03bc9ebd2696f86564e84f1cc800abe27`.

Actual main-source validation passed three CTests in each configuration, 23 OpenMP equivalence/transaction cases, and a no-OpenMP eligible 4096³ full-output comparison. The matched campaign used runtime-default GNU OpenMP waiting, unset `OMP_WAIT_POLICY`/`GOMP_SPINCOUNT`, and a 20 ms parent park outside each API interval; both persistent processes reported 64 workers on CPUs 0–63. Every raw sample is retained.

| FP32 N | Paired repetitions | Frozen V3 API mean | V4 API mean | Ratio of API means | Faster V4 calls |
|---:|---:|---:|---:|---:|---:|
| 4096 | 11 | 34.2623 ms | 32.8583 ms | 0.9590 | 10/11 |
| 8192 | 11 | 273.2435 ms | 252.5215 ms | 0.9242 | 11/11 |

These are complete API timings from this campaign, subject to shared-host contention. A separate 2026.1 GNU oneMKL reference used N=4096/8192 and five workloads, three samples each. Its FP32 API means were 16.7873/223.0538 ms and its SGEMM means were 18.7975/139.6060 ms. This campaign explicitly used passive OpenMP waiting and differs from the matched campaign; do not combine these values into a matched speedup. The raw file lacks per-call MKL observations and preserves only their recorded mean.
