# V4 搜索的成本模型

本轮保留 V3 的完整 API 作为对照，将硬件峰值、实际地址上的计算阶段、完整 API 分开测量。热寄存器微基准的峰值不能直接作为 GEMM 达成率。当前不能获取硬件性能计数器，因此下列字节数是指令层面的逻辑访问量，不是测得的 DRAM 流量。

## INT8-36 为什么值得试，但还没有性能结论

Intel 的 [Optimization Reference Manual, Volume 1, 248966-050](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)，第 20 章给出 AMX 的指令吞吐与 tile 形状。满形状 INT8 点积一次覆盖 K=64，BF16 覆盖 K=32；它们的点积指令吞吐相同。下面只比较 M、N、K 分别整除 32、32、64 的情形。尾块必须按实际发出的指令另计。

| 项目 | V3 FP64 p21 | INT8-36 原型 |
|---|---:|---:|
| 每个分量矩阵积的微块 | 32×32×32 | 32×32×64 |
| 每个微块的点积指令 | 4 | 4 |
| 分量矩阵积数量 | 21 | 36 |
| 点积指令总数 | 4×21×(M/32)×(N/32)×(K/32) | 4×36×(M/32)×(N/32)×(K/64) |
| A/B tile 逻辑加载量 | 每个上述微块 4096 B | 每个上述微块 4096 B |

因此 INT8-36 的点积指令数和上述加载量都是 V3 p21 的 **6/7**。仅靠 INT8 的每周期运算数翻倍，理想速度优势也只有 **7/6≈1.167 倍**；36 个积的成本不能当成 21 个积。潜在的更大收益来自移除每个 BK 上反复进行的浮点转换和重建。

在 V3 p21、重建 batch=2、BK=256 时，每个输出元素、每个 BK 的逻辑访问为：

- AMX 写 FP32 临时结果：`4×21=84 B`。
- SIMD 读这些临时结果：`4×21=84 B`。
- 11 批 FP64 C 的读和写：`16×11=176 B`。

合计 **344 B/输出元素/BK**，不包括 A/B、索引、最终提交和初始化。INT8 原型的八个整数对角线每个 BK 各读写一次 INT32 C，合计 **64 B/输出元素/BK**；所有 K 完成后才读八个对角线并做一次重建。两者走过的缓存层次不同，不能用这个比值直接预测实际加速。

INT32 对角线保持所有 K 的精确整数和，因而允许调整 BK、产品顺序和宏块而不改变整数结果。V3 的浮点累加顺序有数值意义，搜索这些参数时必须重新验证。整数方案还增加了分片打包、整数到 double 的最终舍入、工作区和异常检查成本，必须在 API 时间中计入。

## 精度是独立的门槛

原型使用每个矩阵一个全局指数、八个有符号 radix-128 数位，选取 `i+j<8` 的 36 个积。INT32 和 INT128 的溢出上界已有推导，但这不证明精度。全局定点量化在输入有很宽的指数跨度、尤其 A/B 指数互相抵消时可能丢失有效产品。

质量程序以完整 binary128 参考检验小输出矩阵，包含 K=1、63、64、65、255、256、257、4096、32768，以及 Gaussian、稀疏、抵消、动态范围、舍入边界、零和有限极值。分别报告标准化误差、V3 比值和 C 的事务性语义。失败结果要保留；不调整阈值来使原型通过，也不把均值上的改进视为所有输入的改进。若原型只适用于有限输入范围，必须明确记录范围，不能替换通用路径。

## 宏块容量与页面翻译

FP64 的存储分片数 `d=3/4/5/6` 分别对应产品预算 `p=6/10/15/21`。A/B 的唯一逻辑载荷为 `2*d*(M*K+K*N)` 字节；N=8192 方阵为 0.75/1.0/1.25/1.5 GiB。私有结果和残差临时量还要单独计入，不能把 `p` 当作存储分片数，或把池的逻辑保留限额当作进程 RSS。

用于筛选宏块的近似活跃载荷为 `2*d*BK*(CBM+CBN)` 字节 A/B 分片，再加 `8*CBM*(CBN+8)` 字节 FP64 C（默认 64 B 行 padding）和 `4096*batch` 字节临时产品。这里只计当前 BK、当前宏块使用的数值数组，不含索引、其它线程共享数据和缓存映射效应，也不代表测得的实际驻留量。

在 BK=256、batch=2、p21 下，V3 的 CBM=128/CBN=256 合计约 1424 KiB；CBM=256/CBN=256 约 2072 KiB，略超每核 2048 KiB L2 的标称容量；CBM=256/CBN=512 约 3352 KiB。p6 的分片数减半，对应 CBM=256/CBN=256 约 1304 KiB。该模型解释了按精度搜索几何形状的必要性，但不能据此认定发生多少 L2 miss；组映射、页面归属、同时活跃的其它数组和 tile 加载提示都需要实测。

页面翻译是另一条独立假设。当前 allocator 只申请 64 B 对齐，没有显式大页提示；本机 THP 设置为 `madvise`。依据 [Linux 官方 THP 文档](https://docs.kernel.org/admin-guide/mm/transhuge.html)，对适用的进程匿名内存范围请求 `MADV_HUGEPAGE` 可以影响页大小选择，且首次缺页可能产生压缩/清页成本。它既不保证成功获得大页，也不证明当前瓶颈是 TLB。实验将比较 4 KiB/2 MiB 对齐与提示开关，仅建议完整、已对齐且完全属于当前 allocation 的页面，保留普通分配失败及 hint 失败的处理语义，并记录实际页面观测。

## 如何报告与局部上限的距离

完整方阵的产品运算计数为 `W=2*N^3*p`；其 AMX 等效吞吐是 `W/time`，用户原矩阵 GEMM 吞吐为 `2*N^3/time`。两者相差产品数，不能混用。N=8192、p21 的 `W≈23.09×10^12`，本轮 161.018 TFLOP/s 寄存器校准对应纯点积时间约 143.4 ms；86.306 TFLOP/s 的小工作集重建混合校准约 267.5 ms。它们省略的实际打包、地址跨度、页面、初始化和 API 语义各不相同，不能称为整个 API 的硬件下限。

最后的复核必须分别报告完整 API、计算重建阶段、相应产品运算计数以及相同工作集条件下的校准。没有 PMU 物理流量时，不从这些逻辑载荷画出一个已测得的 DRAM roof，也不把某个百分比写成整机硬件利用率。

## 实验循环

每个实验依次记录假设、实现差异、数值门、同批 profile、分析和下一次修改。先运行保持 V3 的实际布局和地址跨度的 control、无逐次非有限检查诊断、无重建诊断，以及可保持语义的延后 FP32 检查候选；诊断路径不能作为数值实现发布。V3 首尾对照和 oneMKL 参考必须来自同批测试。

搜索优先使用已有数据解释计算阶段距离局部上限的差距，然后扩展 BM/BN/BK、tile 加载方式、布局和预取。最终选择依据完整 API 时间、精度及异常/别名语义，阶段时间仅用于定位瓶颈。未测得的候选和理论成本不能写成实际性能提升。
